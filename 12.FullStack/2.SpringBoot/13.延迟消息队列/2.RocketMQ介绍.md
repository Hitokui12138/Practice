# RocketeMQ
## 主流消息队列
1. RabbitMQ
2. RocketMQ
3. Kafka
- 还有ActiveMQ
## 为什么选择RocketMQ
1. 我们需要的是一个`延迟消息队列`, 类似于定时器的功能, 需要在特定的时刻让队列推送给服务器一个消息(被动触发)
2. 普通的消息队列
    - 是服务器主动去服务器中取得消息(主动获取)
3. RocketMQ自带延迟消息队列, 其他工具则需要安装插件
## 订单过期状态的3种解决方案总结
1. 三种方案
    1. create_time + expireTime = expireTimePoint 与Now比较
    2. 直接记录expireTimePoint到数据库
    3. 使用延迟消息队列, 到时间更改Status
2. 优点: 可以直接通过Status这个值来查询过期的订单
3. 缺点: MQ不能百分百准确
4. 解决方法:
    1. 尽可能提高准确率
    2. 做一个脚本定期扫描数据库, 如果状态没有更改, 则更改
        - 不能放到当前的APP里, 应该做一个第三方的离线脚本
        - 一天, 一个月, 或者服务器负责非常低的时候扫描

## 为什么要选择消息队列
1. `异步`提高性能
    - 从异步的角度提高系统的性能
2. `解耦`
    - 如果把所有功能都放在一个程序里面的话会难以维护, MQ是一个很好的中间件
    - 从代码的模式上面降低了系统的复杂性
    1. (同步的例子)比如A只生成订单, B来处理订单
        - 但不能让B去频繁轮询数据库, 因此可以让A生成订单后加入消息队列, 然后再让B去消息队列中取得, 这样MQ充当一个中间件
        - 这样也可以将一个大团队分成两个子团队
    2. (异步的例子)下单后, 前段要等待后端返回下单成功的消息
        - 这个过程中会做非常复杂的处理, 比如发送短信,仓储调度等等业务流程,如果是同步的话, 会非常慢
        - 可以让后端仅仅进行金额呀优惠券的基础校验后直接返回成功消息, 其他复杂处理可以用异步的方式, 以一个个消息`加入消息队列`中
        - 好处在于可以`控制这些业务执行的频度`,之后再慢慢处理, 同一时间点服务器的压力也会减小(`消峰`的作用)
        - 处理完一个消息后,再去MQ中取得下一个消息
3. 另一种处理方式, 开启一个新线程(中间件的作用)
    - 下单后, 开启一个新线程处理发送邮件等操作
    - 缺点在于`没有解耦`, 还是把相关的功能集成在一个APP里面了
    - MQ可以部署在另一个服务器上面,起到`中间件`的作用, 把复杂的业务分摊到其他机器上面,形成一个集群
4. 还有有很多系统是 `消息/时间驱动型`系统

## Redis与RocketMQ
1. RocketMQ的消息到达率更高
2. 有容错机制
3. 缺点在于非常占用内存
4. 中小型应用就用Redis就好
