# SKU设计 延迟思考, 逐层深入
## SKU属性
1. 常规属性
    1. id, title, img
    2. price, discountPrice
    3. spuId, categoryId, rootCategoryId
2. 其他
    1. json specs, 表达完整的规格名和规格值
        - 是比较复杂的数据结构,类合对象
        - 把对象序列化成字符串再传入sql
        - 一个SKU有多种规格, 因此数组
            - {{k,v},{k,v}}
        - 单独建一个Model, 不过因为不是表, 不需要@Entity
    2. String code, 每个SKU必须有一个唯一标识
        - 具有程序可解析性, id则不行, 前端要用
        - 用户必须选择完整的规格从而形成完整code码之后,才被视为选好一件SKU
        - `15$1-19#6-28#7-2`,表示一个完整的SKU
        - 自定义协议
    3. Long stock, 库存量
3. 规格相关设计
## SKU规格设计(服务端) spec, attribute
1. Spec
    - spec_key, 颜色, 尺寸, 尺码
    - spec_value, 橙色, 蓝色; S,M,L,XL
2. 新表 spec_key,规格名表
    1. id, name, discription
    2. String unit, 规格的单位
        - 英寸, 个, 米
        - 也有主观定义出来的
            - OLED+塞尔达
    3. Integer standard, 规格的标准
        - 是否是标准规格?及要不要使用标准XX库
3. 新表 spec_value,规格值表
    1. id, spec_id(一对多)
    2. name 规格值
        - 红橙黄绿青蓝紫
    3. 这个表与SKU是什么关系
        - 多对多的关系, 因为有些规格是可以复用的
        - 太复杂
4. 新表 spu_key, 多对多关系表
    - 对于一个商品, 颜色尺寸大小的规格是确定的, 因此应该构建SPU与specKey之间多对多的关系
    - id, spu_key, spec_key
5. 新表 sku_spec, 多对多关系表
    - id, spu_id, sku_id, key_id, value_id
    - 为什么这么多?
        - 只是冗余字段,记录一下spu和key

5. 总结
    - Spu - Spec_Key 多对多
    - Sku - Sku_Value 多对多
    - Spu - Sku 一对多

## 完整的数据库并不代表就是一个好的数据库
- 并不只是表达数据之间的关系, 还应该考虑前端的使用
1. 数据完整性
    - 就比如SPU与规格有关联,那么就直接做导航属性, 查询Detail时,相关数据都能返回给前端
2. 前端实用性
    - 前端使用是否方便?
