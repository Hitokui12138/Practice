# 分类表的设计
1. 常见的二级分类(垂直电商)
    - 服装
        - 衬衫
        - T恤
    - 鞋子
    - 居家
2. 如果不确定分类有多少级, 可以选择四级分类
## 方法1:通过二维数据表形成树状结构(常见)
1. 属性
    1. id,name,description
    2. is_root
        - =1时为一级的根分类, =0为其他分类
        - =1时, parent_id=null
        - 真正的树状图应该有一个唯一的根节点,但对业务没有意义, 因此把第一层子节点视作根节点
    3. parent_id(核心)
        - 并不是外键, 用于标注某一个分类的父级分类的ID号
        - 只要让每个节点都记住父级的id,就能通过二维数据表形成树状结构
    4. img,index(人为排序用),
    5. online(下架用)
    6. level(层级多时,便于查询)
2. 缺点
    1. 如果有四级五级分类的话, 上面这个方法插叙效率低
    2. 正向查询(查询服装下的子节点)
        1. 查询所有parentId为服装的id的节点
    3. 回溯查询(已知一个四级节点,查询所有父级节点)
        1. 先查三级,再查二级,再查1级,要查很多次
## 方法2:路径表示法
- 无限级分类的数据表达方式(自定义协议路径)
- 加一个路径字段,像是URL那样, `/node1/node2/node3`
- 这样所有的查询中的WHERE可以在Java中组装好再查
- 这种方法更加灵活,甚至可以在里面写入节点的名称
    - `/node1#衣服/`
    - 也可以自定义协议,规定#等符号的功能便于跳转
- 缺点是需要写java代码, 占用了数据库的空间资源,但远小于高频次查询

# Category相关接口
## 业务
- 在分类页面
    - 点击rootCategory, 可以查询出所有2级Category
    - 点击2级Category, 跳转到所有SPUList页面
- 在首页
    - 有点击rootCategory,跳转SpuList的功能
## 查询2级SpuList
- Spu表有两个Category相关的字段
    - `root_category_id`和`category_id(二级)`的字段
    - 按道理应该只需要category_id就好,但为了查询效率,这里加一个冗余字段

## 代码
```java
// Controller
@GetMapping("/by/category/{id}")
public PagingDozer<Spu, SpuSimplifyVO> getByCategoryId(
        @PathVariable @Positive Long id,
        @RequestParam(name = "is_root") Boolean isRoot,
        @RequestParam(defaultValue = "0") Integer start,
        @RequestParam(defaultValue = "10") Integer count
    ){...}
//Service
public Page<Spu> getByCategory(Long cid, Boolean isRoot, Integer pageNum, Integer size){
    Pageable page = PageRequest.of(pageNum, size);
    return this.spuRepository.findByCategoryIdOrderByCreateTimeDesc(cid, page);
}
//repository
Page<Spu> findByCategoryIdOrderByCreateTimeDesc(Long cid, Pageable pageable);
```
## JPA命名规则
- 只要命名规范,JPA就能推断出“SELECT * FROM spu WHRER category_id = cid”
- 这种机制方便,但是方法名过长,难以处理复杂查询

## Java Bean的问题
- 现在封装好的VO(Paging等等)理论上来讲都是JavaBean
- JavaBean提倡不要在里面写业务逻辑
- 只要不像是Service那样写大量的逻辑即可
- 在构造函数里写少量是可以的
