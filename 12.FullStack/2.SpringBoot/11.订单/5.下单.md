# 下单
## 预扣除库存
1. 下单成功, 但没有支付时扣除库存
    - 避免超卖
    - 但是如果最终没有支付, 库存需要还原
## 库存扣减
1. 乱序思维
    1. 多个订单同时下单时(多个线程)
        - `绝不能认为先进来的线程就会先执行某个方法`
        - 这是由CPU决定的
2. 情况分析
    1. 件数 <= 库存
    2. 件数 > 库存
        1. 库存出现负数
            - 此时应报错
    3. 如果在数据库上加锁的话, 可能出现排队的情况
        - 订单一获得锁, 订单2,3需要排队等待锁的释放
        1. 在数据库上加 行锁
        2. java代码中加锁
3. 思考
    1. 第一种
        1. 减库存之前先查询数据库的库存, OK的话再进行减库存操作
        2. 错误的, 还是因为与之同时, 另一个线程可能执行减库存的并发操作
        3. 总结:`先查询数据库, 然后根据结果进行数据库操作这样的思想是不对的`
            - 这两条SQL之间有时间间隔, 不是一个原子操作
    2. 第二种
        1. 使用事务?
            1. 错误的, 事务 != 锁
            2. 就算在SpringBoot里面加上事务, 还是可能多个事务同时运行, 造成负数库存
    3. 锁
        1. 方法1: 在 Java代码中加锁
            - 这样的操作在分布式中这样是无效的
        2. 方法2: 数据库中加上悲观锁, 不是数据库特有机制
            - 性能会比较差
        3. 方法3: 乐观锁, 并没有实际上的锁, 是一种并发竞态思想
## 锁
1. Java中加锁
    - 三个线程谁先拿到锁,谁先运行, 没有拿到锁就排队
    - 在分布式系统中, 多个java程序就各自算有锁, 最终目标数据库没有上锁, 还是会导致负数库存
2. 悲观锁
    1. 开启事务
        1. 查询Sku的stock
            - 加上sql的锁`for update`,锁定这一条record
            - 在事务结束之前不会解锁
        2. update set
        3. commit
    2. 事务与锁没有联系, 只能保证操作的`原子性`, 还是需要手动加上一个`行锁`
    3. 高并发时频繁加锁解锁性能不好
    4. 另外Mysql的索引有问题, 有可能导致加一个行锁结果把整张表锁定
3. 乐观锁(乐观并发控制)
    1. 把这两条sql写成一条sql
        ```jpql
        update Sku s 
        set s.stock = s.stock - :quantity
        where s.id = :sid
        and s.stock >= :quantity

        //或者也可以先查询version, 然后更新时要求前后version相同
        ```
    2. 在update的同时做最终判断
