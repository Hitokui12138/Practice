# 简单的API都做完了, 后面是业务复杂的API
1. 创建优惠券 在CMS里面做编辑工具
    1. 优惠券类型 参数
        1. 满减券 满多少, 减多少
        2. 无门槛全场券
2. 优惠券审核(非必须)
3. 优惠券投放
    1. 用户领取
        1. 定时? 用户需要抢券
        2. 直接发放给客户, 新用户优惠券
4. 使用优惠券
    1. 金额结算
        1. 预先在购物车或者结账页面计算一次(前端算一次)
        2. 优惠券核销(后段需要核算)
5. 用户退款
    1. 十件商品全部退款
    2. 部分退款, 应该返回多少钱?
        - 优惠金额平坦, 分布权重
## 针对整个优惠券系统有两个概念
1. 模版(可复制的)
    1. 满减券模版, 
        - 只要选择发放时间, 投放时间等等就能快速生成优惠券
2. 活动
    1. 情人节活动, 各种各样优惠券
        - 1000-50, 全场-10, 0.95折
    2. 把投放和领取的过程抽象为活动
3. 品类
    1. 不可能所有优惠券都是全场券
    2. 与分类Category挂钩?
        - 一级分类还是二级分类?
    3. 只和几种特定的商品挂钩
## Model
1. Activity
2. ActivityCover
3. Coupon
4. UserCoupon 多对多关系表
    - 这个关系表有业务意义, 因此需要建Model

## 分析两种关系定义下的数据库设计
1. 优惠券 -> 分类
2. 活动 -> 分类
3. 案例1: 某个商品可以使用的优惠券
    1. SPU -> Category -> Coupon
        - 查询方便, 但是如果和Category强相关, 则相同模版的优惠券需要建多个才能满足不同Category的商品
    2. SPU -> Category -> Activiy -> Coupon
        - 可以简化CMS的操作
4. 不过还是考虑性能, 因此使用方法1
