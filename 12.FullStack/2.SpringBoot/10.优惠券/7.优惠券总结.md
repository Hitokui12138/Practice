# 优惠券总结
1. 业务分析
    1. 通过CMS创建优惠券
        - 优惠券模版, 只要在特定的Activity上指定时间即可
            - 优惠券过期与否取决于Activity的过期时间
        - Coupon代表是一个模版, 并不是真正一张张Coupon
    2. 通过活动发放优惠券
        - 一个活动多个优惠券, Activity:Coupon 一对多
        - 活动的过期时间就是Coupon的过期时间
    3. 优惠券不都是全场券
        - 与Category相关, 一个优惠券可用与多个Category,一个Category也可用多种优惠券
        - Category:Coupon 多对多
    4. 点击商品显示商品可用的优惠券
        - JPQL的用法
    5. 用户领取和使用优惠券
        1. 一个用户可以领取多张优惠券, 由于优惠券不限量, 因此一个优惠券也能被多个用户领取
            - User:Coupon 多对多
    6. 退款时的处理, 优惠券过期问题
2. 数据库
    1. 从Activity入手
        - Activity -> Coupon <-> Category
## 通过活动发放优惠券
1. 点击Activity进入可领取的Coupon一览
    1. ActivityPureVO精简Activity, 没有CouponList
        - BeanUtils.copyProperties
    2. CouponPureVO精简Coupon, 没有CategoryList
    3. 二级精简ActivityCouponVO extends ActivityPureVO
        - 在这个里面添加List<CouponPureVO>
        - 方法比较特殊
    4. 由此获得不含CategoryList的某个Activity的Coupon信息
2. 点击商品查看可用的优惠券一览
    1. 已知spu的categoryID cid 和当前时间
        - SELECT Coupon JOIN Activity JOIN Coupon_Category
    2. 使用`JPQL`的话, 可以不操作第三张表
        - select Coupon join c.categoryList join Activity 
## 用户领取优惠券
- uid, 优惠券cid
1. 考虑使用Map来存储多个用户, hashMap线程不安全, 因此使用ThreadLocal<Map>
    1. static Map
        1. 导致所有请求共享同一数据源, 并发读写可能导致数据错乱
        2. 用户数据无限增长，最终OOM
    2. static ThreadLocal<Map>
        1. 每个请求线程有独立数据副本, 天然线程安全
        2. 配合拦截器可及时清理内存
            - 避免内存泄漏
        3. 隔离不同用户请求
2. static ThreadLocal
    - static本身表示ThreadLocal是`全局唯一`
    1. 请求到达 → 线程池分配线程T1
        - T1操作 threadLocal.get().put("user", userA)
    2. 并发请求 → 线程T2处理
        - T2有自己的独立Map
        - threadLocal.get().put("user", userB)
    3. 请求结束 → 必须调用 threadLocal.remove()
3. LocalUser类
    - 使用PermissionInterceptor 初始化LocalUser和请求结束后清理
4. 领取优惠券
    1. 检测是否存在,是否过期等等
    2. 登陆UserCoupon表
