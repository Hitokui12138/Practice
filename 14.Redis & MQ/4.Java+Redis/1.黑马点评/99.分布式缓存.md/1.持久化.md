# Redis的持久化
1. RDB, Redis Database Buckup File, Redis备份文件/数据快照
2. AOF, Append Only File, 可以看作是命令的日志文件/追加文件
## RDB
- 把内存中`所有数据`, 都记录到磁盘中, 当Redis实例故障重启后, 从磁盘读取快照文件,恢复数据
1. RDB快照文件
    1. 默认保存在当前运行的目录
2. 如何手动生成快照?  
    1. 直接阻塞主线程(不推荐),
        1. 进入`redis-cli`
        2. 使用`save`命令
            - 主线程会`被阻塞`, 直到执行完毕, 返回ok
        3. 执行ctrl+C退出时, 也会自动save一次, 因此日常停止Redis不会丢失数据
    2. 推荐使用子线程
        1. 进入`redis-cli`
        2. 使用`bgsave`
            - 开启一个子进程执行RDB, 主线程不受影响
        3. 每隔一段时间自动save的机制走的是bgsave
3. 每隔一段时间自动RDB一次(自动备份)
    1. 在`redis.config`文件中
        1. `save ""`, 表示禁用RDB
        2. `save 300 100`, 300内发生10次修改, 则备份一次
4. config文件中RDB相关的其他设置
    1. `rdbcompression no`
        - 要不要压缩 RDB文件, 推荐不要开启, 压缩也占用cpu
    2. `dbfilename dump.rdb`
        - RDB文件的文件名
    3. `dir ./`
        - RDB文件保存目录
5. RDB问题:
    1. 两次RDB之间间隔比较长,可能造成数据丢失

## AOF
- 出现问题后, 把所有命令再执行一遍
1. AOF文件的格式
    - 比如一个命令`set num 123`
    ```
    $3
    set
    $3
    num
    $3
    123
    ```
2. 手动开启AOF
    - AOF机制默认是关闭的
    1. `appendonly yes`
    2. `appendfilename "appendonly.aof"`
3. 其他
    1. `appendfsync always`, 同步刷盘
        - 这都是主进程完成的, 相当于一次命令=操作内存+写入磁盘
        - 安全, 但是性能不好
    2. `appendfsync everysec`, 默认方案, 每秒刷盘
        - 命令会暂存入AOF缓冲区中, 每隔一秒, 把缓冲区输入一起写入文件
        - 主进程只写内存, 写磁盘操作由其他线程处理
        - 会丢失一秒钟内的操作
    3. `appendfsync no`,几乎不用
4. AOF的问题
    1. AOF文件很大, 比RDB大
    2. 对同一个key多次操作, 其实只有最后一次才有意义
5. `bgrewriteaof`, 重写/优化 AOF文件
    - 在cli中执行, 命令是后台执行的
    - 执行后, 会去掉重复操作, 还会把多个set合并成mset
    - 还有一些压缩编码处理
6. 重写aof文件的自动触发
    1. `auto-aof-rewrite-percentage 100`
        - AOF文件比上次文件 增长超过多少百分比时触发重写
    2. `auto-aof-rewrite-min-size 64mb`
        - 按大小进行重写

## 开发时两者都会使用
1. RDB, 文件小, 恢复快, 可以忍受数分钟数据丢失
2. AOF, 文件大, 恢复慢, 但是对数据能完整回复
