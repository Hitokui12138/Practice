# 三大问题
1. 缓存穿透
    - 请求的数据在`缓存和数据库都不存在`, 缓存不生效, 所有请求都打到数据库
    - 穿透了Redis, 总是打到数据库
2. 缓存雪崩
    - 同一时间, 大量缓存key过期失效或者Redis宕机, 大量请求打到数据库
3. 缓存击穿
    - 热点Key过期(高并发访问的key, 缓存业务重建复杂的key),  大量请求打到数据库

## 缓存穿透
1. 缓存空对象
    - `cache:shop:key` | `""`, TTL短一点
    - 实现简单, 但有额外的内存消耗, 以及短时间的不一致
    1. 解决
        1. 设置一个短一点的TTL
2. 布隆过滤
    - 这是一种算法, 在`客户端到Redis之间`加一个布隆过滤器
    - 布隆过滤器会先判断查询数据是否存在, 存在时才放行
    - 类似一种byte[], 会把Redis的key根据hash值计算后保存在这些位里
    1. 并不是百分百, 存在误判可能
        1. 布隆过滤器认为不存在时, 百分百不存在
        2. 认为存在时, 不一定存在
    2. Redis提供的BitMap可以简化布隆过滤器的开发

## 缓存雪崩
1. 解决方案
    1. 给不同Key的TTL增加随机值
    2. 利用Redis集群提高Redis本身的可用性
        - 主从复制 + 哨兵机制
    3. 给服务添加降级限流策略
        - 快速失败, 拒绝服务
    4. 给业务添加多级缓存

## 缓存击穿
1. 热点Key怎么来的?
    1. 高并发访问, 秒杀商品
    2. 缓存重建业务复杂, 多个表联合计算得出的结果
2. 解决方法
    1. 用互斥锁(悲观锁)的方式, 只要一个请求来创建Key就好
        - 若一个线程获取锁失败, 那么休眠一下或者返回错误消息, 再重试
    2. 逻辑过期
        - 干脆不要给热点key设置TTL, 给Value中加一个逻辑上的ExpireTime
        - 然后活动结束再移除即可
