# 最佳实践
1. 高一致性的场景
    1. 读操作
        1. 缓存命中直接返回
        2. 未命中则查询数据库, 并写入缓存, 设定超时时间
    2. 写操作
        1. 先写数据库, 然后再删除缓存
        2. 要确保数据库与缓存操作的原子性 加一个@Transactional

# 缓存更新策略
1. Redis有自己的内存淘汰机制, 也可以自定义
    - 内存不足时自动淘汰部分数据, 下次查询更新缓存
    - 但淘汰的数据是不我们能控制的, 难以保持数据一致性
2. 超时剔除
    - 利用expire命令增加TTL时间
    - 一致性: 有时间间隔, 因此不是强一致性
3. 主动更新
    - 每当修改数据库时, 更新Redis
    - 先改后删(使用`消息队列`实现)
## 主动更新也有三种策略
1. Cache Aside Pattern (CAP 推荐)
    - 由缓存的调用者, 在更新数据库的同时更新缓存
2. Read/Write Through Pattern(不推荐)
    - 缓存与数据库整合成一个服务, 由服务来维护一致性, 调用者无需关心
3. Write Behind Caching Pattern(写回, 不推荐)
    - 让调用者只操作缓存, 由其他线程异步将缓存数据持久化到数据库,保证最终一致性
    - 有一个线程会监视缓存是否发生变化, 若变化, 则一括(合并成一次SQL操作)更新到数据库
## CAP
1. 删除缓存, 更新数据库时让缓存失效, 再有人查的时候更新缓存
2. 保证更新数据库和缓存两个操作的原子性
    1. 单体系统可以放在一个事务里面
    2. 分布式系统: 利用TTC等分布式事务方案
3. 线程安全问题(两个操作: 1. 更新数据库, 2. 更新缓存)
    - 应该先操作数据库, 再删除缓存
