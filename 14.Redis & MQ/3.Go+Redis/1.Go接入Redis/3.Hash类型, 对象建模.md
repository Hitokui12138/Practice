## 一.Hash底层原理
- Hash的本质 (Key : ( K : V )), 两层KV
- 用于保存用户对象,商品信息等简易JSON结构
1. Redis的Hash有两种编码结构
    1. `listpack/ziplist` (小对象)
        - 在配置中设置阈值, 若value的长度/field数量`超过阈值`,则转化为hashtable
        1. 结构
            - [k1|v1|k2|v2|k3|v3]
            - 相当于是一个数组, 是一段连续的内存, CPU缓存友好
            - 没有指针(指针也是占内存的) 
        2. 传统hashtable的问题
            1. 指针多, 内存浪费, CPU缓存差
    2. `hashtable` (大对象)
        - bucket
        - hash索引
        - 指针引用
2. 渐进式rehash
    - hash的数量扩容后, 可能会遇到hash冲突, 命中冲突后开始迁移, 这个过程叫rehash
    - Redis的rehash是渐进式的(每次从原表搬过来一部分), `防止阻塞主线程`
        - 使用IO的epoll()的wait, 只执行一小段时间(毫秒)
3. hash操作
    1. HSET()
        - `HSET user:1001 name hitokui age 20 city shanghai`
        - `HSET [hkey] [k1] [v1] [k2] [v2]`
    2. HGET()
        - `HGET user:1001 age`
        - `HSET [hkey] [key]`
    3. HINCRBY()
    4. HGETALL() , 这个操作大对象时很危险 
        - `HGETALL user:1001`, 拿到的是一个Map
## 二.对象建模
1. 为什么`不用String存储JSON`
    - 如果是读多写少的小JSON的话可以用String
    1. 如果使用String, CPU消耗高, 并发冲突大
        1. 读取JSON, 反序列化(而且JSON大时更容易发生并发冲突)
        2. 修改
        3. 重新写入
    2. Hash操作都是 O(1)
2. Key设计规范
    - user:{id}, 作为这个Hash的Key, 尽量不要使用下划线
3. 不要把Hash当作数据库用
    1. 严禁:
        1. 超大Hash, 上万字段
        2. 不要存日志
        3. 不要存历史记录
    2. 适合:
        - 中小对象
        1. 某个文章的点赞, 基础信息
        2. 时刻注意字段是有限的
## 三.应用: 用户资料管理系统
1. 需求
    1. 创建用户时, 加入Redis的Hash中
    2. 更新字段, 查询字段, 查询全部资料
2. 
    ```go
    // 1. HSET
    err := client.HSet(ctx, key, map[string]interface{}{
		"name": "张三",
		"age":  18,
		"city": "上海",
	}).Err()

    // 2. HGET
    string,err := client.HGet(ctx, key, field).Result()

    //3. HGETALL
    map[string]string, error := client.HGetAll(ctx, key).Result()
    ```
