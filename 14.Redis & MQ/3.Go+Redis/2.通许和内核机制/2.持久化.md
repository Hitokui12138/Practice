# Redis的持久化
## 一. 持久化的意义
1. Redis为什么需要持久化?
    1. 内存数据库,一旦进程退出, 数据就会丢失
    2. 因此需要把内存数据写入磁盘
2. Redis持久化的目标?
    1. 并不是要求强一致性,并不需要当作数据库用
    2. 减少数据丢失
    3. 快速恢复事务
## 二. 持久化的方式
### RDB 快照, Redis Database Backup
1. `RDB`持久化机制(快照)
    1. 使用某一时刻Redis内存的完整快照, 生成文件 dump.rdb
        - 这是一个二进制文件, 体积小, 恢复快
    2. 使用子进程实现, `主线程不会中断`
2. RDB执行流程
    1. Redis会Fork一个子进程
    2. 通过子进程生成数据快照
    3. 写入 dump.rdb
    4. 替换旧文件
3. 问题
    1. Fork 表示当前的进程会被拷贝一份, 这意味着内存占用会翻倍, 一定要确保有额外内存能执行这个
    2. Fork命令后, 在持久化期间, 主线程还在继续接收请求, 若此时主线程挂掉, 期间的数据将会丢失
4. RDB的配置
    1. `save 300 10`, 在300秒内, 发生10次修改, 则持久化一次
        - 可以配置多条指令, 不要太频繁
    2. `BGSAVE`, 手动后台生成
    3. 禁用`SAVE`, 这个会阻塞主线程
### AOF 刷盘/重写命令 Append Only File
- 就是记录所有`写的命令`, 然后恢复时就会重新执行这些命令
1. 什么是`写命令`
    - SET, INCR, HSET等等
3. AOF重写机制
    1. 指令的日志可能越写越长
        - `AOF Rewrite`重写指令日志, 会自动生成最小命令集合
            - 比如执行 INCR 1000次, 重写后变成SET counter 1000
4. AOF优点:
    - 安全性高, 可回放, 日志可读
5. 缺点
    - 文件大
    - 恢复慢, 要一条条执行
    - 写入成本高
## RDB 和 AOF的选择策略
1. 只使用RDB的场景(丢一点数据也没关系)
    - 缓存(还能重新从数据库加载回来), 排行榜, 统计
2. 只使用AOF的场景
    - 用户状态类(一定不能变), 轻量业务数据
3. 生产推荐 RDB + AOF
    - 恢复快, 数据也更安全
    1. 常见生产配置
    - `appendonly yes`, 
    - `appendfsync everysec`, (推荐)刷盘逻辑是每秒执行一次, 最多丢一秒数据
