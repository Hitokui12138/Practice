## Redis Stream
1. 之前学的队列 List + BRPOP的缺陷
    1. 没有消费确认
    2. 没有失败尝试
    3. 没有消费组
    4. 没有消费历史
2. Pub/Sub 发布订阅的缺陷
    1. 没有持久化机制
    2. 消息不可追溯
    3. 离线消费者会丢失信息
3. Stream
    - 本质上是一个`可持久化的日志流`, 可追加的日志
        - 类似于 `Kafka 的Partition`
    1. 核心能力
        1. 消息持久化, 可以进行历史数据重放, 故障恢复
        2. `ACK确认`, 返回成功或失败的结果
        3. 消费组, 
        4. PendingList
    2. 消息结构
        - 消息ID + KV
## 操作RedisStream
1. 添加
   - `XADD user_stream * user 1001 money 99`
   - `XADD user_stream MAXLEN 1000 * user 1001 money 99`
2. 读取
    - `XREAD STREAMS user_stream 0`, 从0开始读
    - `XREAD BLOCK`
    1. 消费者组
        1. 创建消费者组
            - `XGROUP CREATE user_stream group1 0`, 基于某个stream创建
        2. 消费新消息
            - `XREADGROUP GROUP group1 c1 STREAMS user_stream >`
                - c1 是消费者的名字 , `>`不能丢, 表示读取最新的消息
            1. 注意, Redis的消费者组内`不能保证消费顺序`, 
                - 如果需要保持顺序, 那么`只能一个组下面一个消费者`
        3. ACK 确认
            - `XACK user_stream group1 msgId`
3. PendingList
    - 保证`可靠性`
    - 如果消费失败了, 消费者可以先跳过这条消息, 对于没有恢复ACK的消息, 会加入到PendingList里面
    - 这样后续就可以重试了
    - `XPENDING user_stream group1`, 查看某个消费者组的pendinglist
