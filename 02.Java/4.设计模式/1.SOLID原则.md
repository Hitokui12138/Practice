# 软件设计模式
## 1. 核心原则SOLID原则
1. 单一职责原则 (Single Responsibility Principle, SRP)
    - 一个类只做一件相关的事情。
2. 开闭原则 (Open-Closed Principle, OCP)
    - 类、模块、函数等应该对扩展开放，对修改关闭
    - 当需要增加新功能时，我们应该通过`增加新的代码`（例如新的子类或实现类）来实现，而不是去修改已有的、工作良好的代码
3. 里氏替换原则 (Liskov Substitution Principle, LSP)
    - 子类应当可以完全替换父类, 子类在继承父类时，不应该改变父类预期的行为
4. 接口隔离原则 (Interface Segregation Principle, ISP)
    - 接口的设计要“专”，不要设计大而全的“胖接口”
    - 避免一个类为了实现接口中的某一个功能，而不得不实现所有其他它并不需要的功能
5. 依赖倒置原则 (Dependency Inversion Principle, `DIP`)
    - 代码的依赖关系应该通过抽象（如接口或抽象类）来建立，而不是具体的实现类
    - 要面向接口编程，不要面向实现编程， 高层模块不应依赖低层模块，两者都应依赖抽象
    - new 关键字（实例化具体类）必须出现在最外层（Main、Config、Controller），永远不能出现在业务逻辑层（Service）。
    1. 依赖关系
        - 原来：高层 → 低层（方向向下）
        - 现在：高层 → 抽象 ← 低层（方向都指向抽象层）
    2. 举例：
        - 电商系统的 CheckoutService（结账业务，高层）需要调用支付接口完成扣款
        ```java
        // 1. 反例
        // 高层业务类
        public class CheckoutService {
            // 直接依赖了具体的第三方实现类
            private AliPayApi aliPay = new AliPayApi(); 
            
            public void checkout(Order order) {
                aliPay.doPay(order.getAmount(), order.getCurrency());
                // 如果明天老板说换成微信支付，你必须要修改这一行代码
            }
        }

        //2. 正例
        // 定义抽象接口
        public interface PaymentGateway {
            void pay(double amount, String currency);
        }

        // 2. 高层业务只依赖自己定义的接口
        public class CheckoutService {
            private PaymentGateway gateway;
            // 通过构造函数注入（DI）
            public CheckoutService(PaymentGateway gateway) {
                this.gateway = gateway;
            }
            public void checkout(Order order) {
                gateway.pay(order.getAmount(), order.getCurrency());
            }
        }

        // 3. 底层实现（适配器）去实现高层的接口
        public class AliPayAdapter implements PaymentGateway {
            private AliPayApi api = new AliPayApi();
            public void pay(double amount, String currency) {
                api.doPay(amount, currency);
            }
        }
        ```
    3. 最后一步装配
        1. 静态配置 配置文件 + @Configuration
            ```java
            // 1. 配置类（属于最外层的“组合根”）
            @Configuration
            public class PaymentConfig {
                
                @Value("${payment.channel}")
                private String channel;

                @Bean
                public PaymentGateway paymentGateway() {
                    // 根据配置，启动时只 new 一个，并交给Spring容器
                    if ("ali".equals(channel)) {
                        return new AliPayAdapter();
                    } else if ("wechat".equals(channel)) {
                        return new WechatPayAdapter();
                    }
                    throw new RuntimeException("未知支付渠道");
                }
            }

            // 2. CheckoutService 完全无感知，只管运行
            @Service
            public class CheckoutService {
                private final PaymentGateway gateway; // 启动时已经注入了固定的那个
                public CheckoutService(PaymentGateway gateway) { ... }
            }
            ```
            1. 为什么能刚好注入这个，Spring 容器（IoC 容器）内部的工作原理
                1. 容器执行@Bean方法，获取对象， 放入放入容器 Map（按类型存储）
                    - Key 是`接口类型` PaymentGateway，Value 就是这个实例
                    - container.put(PaymentGateway.class, aliPayAdapterInstance); 
                2. 然后创建PaymentGateway实例时，会找到这个对象
                3. 如果有多个实现则会报错， 用@Qualifier("aliPayAdapter")解决
        2. 动态配置， 让用户选择
            - 但是千万不能在 CheckoutService 里面写 if (type.equals("ali"))
            - 正确的做法是引入一个 工厂（Factory） 或 策略上下文（Context），将“决策权”从业务层剥离出去。
            - PaymentGateway gateway = factory.getGateway(userSelectedChannel);
            1. 工厂方法中可以写if-else，switch
            2. 也可以用 Map<String, PaymentGateway> gatewayMap;替换if-else
                - 原理：1. 核心原理：Spring 的`自动收集`机制
                1. 当你在一个类中声明了 Map<String, PaymentGateway> gatewayMap 并加上 @Autowired 时，Spring 容器会执行一个特殊的注入逻辑：
                2. 识别目标类型：Spring 发现需要注入一个 Map，其 Value 的类型是 PaymentGateway。
                3. 查找所有匹配 Bean：Spring 会在容器中查找所有类型为 PaymentGateway 的 Bean。
                4. 组装成 Map：Spring 会自动将这些 Bean 组装进这个 Map 中。其中，Key 是 Bean 在容器中的`名称`（默认为类名首字母小写），Value 就是 Bean 的实例。Spring 官方文档明确说明了这一行为。

## 2. 设计模式分类（三大类）
1. 创建型模式 (Creational Patterns)
    - 关注点：`对象的创建过程`。它们隐藏了对象创建的复杂逻辑，使得我们无需直接使用 new 关键字。
    1. 单例模式 (Singleton) 五星
        - 保证一个类在全局只有一个实例，并提供一个统一的访问入口
        - 如配置管理、日志记录器。
    2. 工厂方法模式 (Factory Method) 五星
        - 定义一个创建对象的接口，但让子类决定具体实例化哪个类，将对象的创建延迟到子类
        - 如各种 Factory 类。
    3. 建造者模式 (Builder) 四星
        - 将复杂对象的构建过程拆解为一步步的“组装工序”，允许通过链式调用生成不同表现的对象
        - 如构造DTO或SQL查询条件。
    4. 抽象工厂模式 (Abstract Factory) 三星
        - 提供一个创建一系列相关或相互依赖对象的“工厂家族”，无需指定它们的具体类
        - 如跨平台UI组件库。
    5. 原型模式 (Prototype) 二星
        - 通过复制（克隆）一个现有的实例来创建新对象，而不是通过 new 关键字重新初始化
        - 如高性能拷贝或避免重复数据库查询。

2. 结构型模式 (Structural Patterns)
    - 关注点：`类和对象的组合。`
    - 通过继承、组合等方式，在不改变原有类的情况下，为其增加新的功能或适配不同的接口。
    1. 适配器模式 (Adapter) 五星
        - 充当“电源转换器”，让原本接口不兼容的两个类能够互相配合工作
        - 如将旧版API适配为新的接口规范。
    2. 装饰器模式 (Decorator) 四星
        - 像“穿衣服”一样，在不修改原有类代码的前提下，动态地为对象附加额外的职责或功能
        - 如Java I/O流中的 BufferedInputStream。
    3. 代理模式 (Proxy) 四星
        - 为原对象创建一个“替身”或“中介”来控制对它的访问，常用于延迟加载、权限校验或日志记录
        - 如Spring AOP。
    4. 外观模式 (Facade) 四星
        - 为复杂的子系统提供一个统一的“门面”接口，让客户端只需调用这一个简单方法即可完成复杂操作
        - 如封装第三方SDK。
    5. 桥接模式 (Bridge) 三星
        - 将抽象部分与实现部分分离解耦，让它们可以沿着各自的维度独立变化
        - 如跨平台画图，形状和颜色分开扩展。
    6. 组合模式 (Composite) 三星
        - 将对象组织成“树形层次结构”，使得客户端在操作单个对象和组合对象时具有一致性
        - 如文件目录树或部门组织架构。
    7. 享元模式 (Flyweight) 二星
        - 通过“共享”已经存在的相似对象来减少内存开销，高效支持大量细粒度对象的复用
        - 如数据库连接池或字符缓存池。

3. 行为型模式 (Behavioral Patterns)
    - 关注点：`对象之间的通信和职责分配。`
    1. 策略模式 (Strategy) 五星
        - 定义一组算法，将每个算法封装起来，让它们可以互相替换，实现算法逻辑和客户端代码的彻底解耦
        - 如支付渠道选择或价格计算。
    2. 观察者模式 (Observer) 五星
        - 定义一对多的依赖关系，当被观察者（主题）状态发生改变时，所有依赖它的观察者都会自动收到通知并更新
        - 如事件监听器、消息订阅。
    3. 模板方法模式 (Template Method) 四星
        - 在父类中定义算法的“骨架结构”，允许子类在不改变整体流程的情况下，重写其中的某些具体步骤
        - 如JUnit测试流程或Spring的 JdbcTemplate。
    4. 迭代器模式 (Iterator) 四星
        - 提供一种统一的方式顺序访问聚合对象（如集合、数组）中的元素，而无需暴露其底层的内部数据结构
        - 如Java中的 Iterator 接口。
    5. 责任链模式 (Chain of Responsibility) 三星
        - 将多个处理者连成一条“链条”，让请求沿着链条依次传递，直到有处理者处理它为止
        - 如Tomcat的Filter过滤器链。
    6. 命令模式 (Command) 三星
        - 将请求（行为）封装为一个独立的对象，从而支持参数化调用、请求排队、日志记录以及支持撤销/重做操作
        - 如Runnable任务或菜单按钮。
    7. 状态模式 (State) 三星
        - 允许对象在其内部状态发生改变时，动态地改变它的行为，看起来仿佛“换了一个类”一样
        - 如订单状态机或电梯运行逻辑。
    8. 中介者模式 (Mediator) 三星
        - 通过一个“中介者”对象来封装一组对象之间的复杂交互，降低它们之间的直接耦合，避免网状调用
        - 如MVC中的Controller或聊天室。
    9. 备忘录模式 (Memento) 二星
        - 在不破坏封装性的前提下，捕获并保存一个对象的内部状态“快照”，以便在将来某个时刻恢复到之前的状态
        - 如游戏存档或IDE的撤销操作。
    10. 访问者模式 (Visitor) 一星
        - 在不修改现有类的前提下，为对象结构中的各个元素添加新的操作，将数据结构与数据操作分离
        - 如解析抽象语法树。
    11. 解释器模式 (Interpreter) 一星
        - 定义一种语言的文法规则，并提供一个解释器来解析和执行该语言中的特定句子
        - 如正则表达式引擎或自定义DSL解析器。
