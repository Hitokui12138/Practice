# 创建者模式
1. 创建型模式 (Creational Patterns)
    - 关注点：`对象的创建过程`。它们隐藏了对象创建的复杂逻辑，使得我们无需直接使用 new 关键字。
    1. 单例模式 (Singleton) 五星
        - 保证一个类在全局只有一个实例，并提供一个统一的访问入口
        - 如配置管理、日志记录器。
    2. 工厂方法模式 (Factory Method) 五星
        - 定义一个创建对象的接口，但让子类决定具体实例化哪个类，将对象的创建延迟到子类
        - 如各种 Factory 类。
    3. 建造者模式 (Builder) 四星
        - 将复杂对象的构建过程拆解为一步步的“组装工序”，允许通过链式调用生成不同表现的对象
        - 如构造DTO或SQL查询条件。
    4. 抽象工厂模式 (Abstract Factory) 三星
        - 提供一个创建一系列相关或相互依赖对象的“工厂家族”，无需指定它们的具体类
        - 如跨平台UI组件库。
    5. 原型模式 (Prototype) 二星
        - 通过复制（克隆）一个现有的实例来创建新对象，而不是通过 new 关键字重新初始化
        - 如高性能拷贝或避免重复数据库查询。
## 1. 单例模式
- 一个单例类在任何情况下都只存在一个实例，`构造方法必须是私有的`、由自己创建一个`静态变量`存储实例，对外提供一个`静态公有方法`获取实例
1. SpringBoot默认Scope就是单例模式，用“容器单例”替代了“编码单例”
    1. 与经典GoF单例模式的区别
        1. GoF： 只能硬编码调用， 手动写： Logger.getInstance()， 违反DIP
        2. SpringBoot使用 `@Service`, `@Scope("singleton")`, 确保对于某个类型（或 Bean 名称），在容器内存中只保留一个实例。
            - 直接使用@Autowired注入，符合DIP
    2. `@Scope`注解,单例无状态，原型存会话，请求用代理，线程本地化
        1. 默认singleton， 无需显式使用
        2. `@Scope("prototype")`, 原型每次获取/注入都创建一个新实例
            - 适用于有状态的对象，比如：用户会话信息、临时计算器
        3. `@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)`
            -  Web 作用域：在 Spring Web 环境中使用
        4. `@Scope(value = "session", proxyMode = ScopedProxyMode.TARGET_CLASS)`， 每个 HTTP Session 一个实例
    3. Spring默认的单例模式意味着什么
        1. Spring 的 @Service、@Controller、@Repository 默认都是单例的。这意味着`多个线程会共享`这个 Bean 的实例。
            - 正确做法： 只注入`无状态的` Service/DAO，或者只定义 `final 类型`的不可变对象。
            ```java
            @Service
            public class BadService {
                // 错误！这是成员变量，所有线程共享，并发修改会导致数据错乱
                private int count = 0; 
                count++；//线程不安全

                // 如果必须单例+持有状态，使用ThreadLocal
                private ThreadLocal<Integer> threadLocalCount = ThreadLocal.withInitial(() -> 0);
                threadLocalCount.set(threadLocalCount.get() + 1);

            }
            ```

## 2. 工厂方法模式
- 在 Spring Boot 中，你很少需要手动去写经典的 XXXFactory.java 类。Spring 的 DI 容器已经替你实现了工厂的职责。你真正要学的，是如何利用 Spring 的 @Conditional（条件注解）或 Map 注入，来“优雅地替代工厂模式中的 if-else”。
- 只有当你发现 new 某个对象的逻辑极其复杂（需要配置、条件判断、依赖其他服务），或者该对象极有可能被替换（如换云厂商）时，才需要用工厂模式
1. 用途
    1.  JDK中的工厂模式： 工厂模式用于创建对象，NIO 中大量用到了工厂模式，比如 Files 类的 newInputStream 方法用于创建 InputStream 对象（静态工厂）、 Paths 类的 get 方法创建 Path 对象（静态工厂）
    2. Spring中的工厂模式： Spring 使用工厂模式可以通过 BeanFactory 或 ApplicationContext 创建 bean 对象。
2. 分为三类
    1. 简单工厂模式
    2. 工厂方法模式
    3. 抽象工厂模式
3. 简单工厂模式（你要什么，跟我说（传参），我帮你造）
    - 把 new 关键字放在工厂里
    - 因为有传参，所以工厂里面有大量的if-else，且后续每新增一个产品，就要改工厂类，违背开闭原则
4. 工厂方法模式
    - 把工厂也抽象成接口。每个具体产品都对应一个具体工厂。
    - 定义 PaymentGatewayFactory 接口，AliPayFactory 实现它，WechatFactory 实现它。业务层选择注入哪个工厂。
    - 解决了开闭原则， 但是工厂具体实现类会大幅增加
5. 抽象工厂模式
    - 你的系统不仅要对接“支付渠道”（支付宝/微信），还要对接“退款渠道”、“对账文件解析”。这些都属于 “同一品牌（`产品族`）” 的产品。
    - 工厂模式的工厂。一个工厂不再只生产一种产品，而是生产 “一整套配套产品”。
    1. `支付、退款`恰好构成了一个完整的`产品族`（同一品牌），而`支付宝和微信`则是`不同的产品族实例`, 每个品牌都必须提供这三个核心服务
