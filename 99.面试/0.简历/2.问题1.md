## 1. 你提到 GSD 结算平台用 Spring Batch 做批处理，Airflow 做调度。这两个是怎么分工的？Spring Batch 本身有 JobLauncher 可以触发，为什么还要加一层 Airflow？
1. SpringBatch主要写业务逻辑, 而Airflow则是负责任务调度编排的工具
2. SpringBatch 自带 JobLauncher 
    1. 不能配置 类似 A跑完再跑B, B如果失败的话不要执行C这样的逻辑
    2. 调度任务依赖@Schedule实现的, 不能统一管理启动和停止
3. Airflow作为统一调度平台，在外部 DAG 配置定时与多任务依赖，并且可以汇总执行结果,便于失败告警与运维

- Airflow是一个调度器



## （错误）2. 日终精算通过 Dubbo 调上游拿原始数据，如果某一次上游系统挂了或者 Dubbo 调用超时，你的批处理链路怎么处理？是重跑整个任务还是只补那一批？
- SpringBatch的逻辑分为 `拉取数据`->`清洗核算`->`生成台账`这三步
1. 首先在我们的项目中, Batch开始执行时,首先先把当日需要的主数据一次性拉取下来(拉取AWS S3的CSV文件)，, 后续不再走dubbo而是都读取这个快照的数据
2. 如果Dubbo调用超时, 也就是没有拿到上游数据, 则当前这个JOB会被标记失败, 
3. 后续待上游恢复，运维传入故障业务日期 + 失败分片标识, 就可以定向补跑异常分片数据, 无需重跑全量 Job

## 1. 如果 B 失败的原因是临时性故障（比如数据库连接池满了），你的 DAG 有重试机制吗？重试几次？重试间隔怎么设的？失败告警发到哪里？
1. 我们在 Airflow 任务上配置重试：重试 3 次，间隔 5 分钟。B 任务出现数据库连接池打满或者Dubbo超时这类临时故障会自动等待重试，重试全部失败才标记任务失败，下游 C 不再执行.
2. 告警信息会通过邮件发送给运营的同事, 运维收到告警，排查数据库连接池满这类问题（调连接池参数、临时扩容），问题修复后，在 Airflow 页面手动重跑 B 任务即可，B 跑成功自动触发 C，不用重跑 A。

# 4. 换个方向。你提到 GSD 项目用了 Redis 做热点缓存。你简历里写"针对高频查询接口进行性能优化，实现 Redis 热点数据缓存逻辑"——能具体说一下缓存的是什么数据？缓存更新策略怎么设计的？比如缓存里的数据和 MySQL 不一致了怎么办？
1. 主要是面向加盟商的热点数据:
    - 加盟商基础档案：加盟商编号、签约费率、结算账户、分佣比例
    - 昨日收益日报：加盟商日汇总收益、待结算金额、已打款总额
2. 先更 DB、后删缓存 + 延迟双删
    - 比如加盟商费率修改、日结算生成、打款完成时：
    1. 数据库事务完成更新 / 落账
    2. 删除对应加盟商缓存 Key
    3. 等待用户下次查询时, 查库后回填Redis, TTL设为12h
3. 对于数据不一致, 我们有一个异步延迟二次删除的兜底策略
    - 在执行删除缓存Key后,我们会向消息队列发送一个再删一次该缓存Key的操作, 可以杜绝大部分由网络异常引起的数据不一致的情况
    - 对于汇总收益 key这种高频访问的Key, 我们没有设置TTL, 而是在凌晨主动刷新, 防止缓存击穿

# 用 RabbitMQ TTL + 死信交换机做延迟关单。下单后发一条带 TTL 的消息，假设 TTL 设了 30 分钟。如果用户在第 29 分钟支付了，你怎么阻止第 30 分钟的关单逻辑执行？是被动等关单时再查一次订单状态，还是有主动取消延迟消息的机制？
1. 我们是根据订单状态控制的, 在消息队列的消费者收到关闭订单的信息时, 首先会查一下订单的状态, 如果是已支付, 自然不会关闭订单
2. 支付那边也是一样的, 如果发现支付时状态为已关闭, 也会提示用户该订单已过期请重新下单

# 你说 GSD 项目用 Dubbo 调上游拿数据，你们当时 Dubbo 的负载均衡策略用的是哪种？服务注册是怎么做的？如果 ZooKeeper 临时挂了，RPC 调用会受影响吗？
1. 用户和运营用的查询类接口是普通随机, 批处理用的是带权重的随机
2. 上游服务提供者在Dubbo启动后, 向 ZK 注册临时节点，写入接口地址、版本、权重; 下游消费者(结算系统)启动时订阅对应服务路径，从 ZK 拉取全量提供者列表缓存到本地内存
3. ZK宕机不会影响RPC调用, 因为现存的消费者可以正常走本地缓存的服务列表, 新增的消费者实例可能受影响, 此时应该将ZK重新上线
