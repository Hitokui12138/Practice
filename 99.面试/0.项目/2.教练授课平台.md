## 1. 微信支付 & 分账、小微商户进件（核心）
1. 服务商模式小微商户自助进件整套 API 流程，需要哪些资质材料上传？接口`回调?`失败如何重试、幂等处理？商户审核驳回如何重试提交？
    1. 首先要准备调用微信v3API所需的服务商商户号、APIv3 密钥, API Key等等配置
    2. 前端需要一个用户输入页面, 包含 身份证正反面 银行卡卡号等信息的页面
    3. 后端准备一个申请记录的数据表, 生成一个唯一外部申请单号, 调用小微商户入件API
    4. 入件审核由微信那边完成, 微信提供查询API可以主动查询审核结果, 也可以用回调地址来被动接收审核结果
    5. 进件成功后, 返回子商户号 sub_mchid, 把这个子商户号保存在数据库中与用户信息绑定
    6. 注意点: 敏感字段必须用微信平台证书 RSA 加密
2. 微信分账订单解冻、分账比例锁定、分账失败资金回流怎么处理？平台抽成逻辑是下单扣还是结算扣？0 元订单、积分抵扣订单会不会触发分账接口？
    1. 下单必须传 profit_sharing=true, 净额会全额冻结在二级商户待分账账户，无法自动提现，只能通过分账 / 完结分账释放资金。
    2. 在学员确认上课完毕后, 后台调用「完结分账」接口, 解冻冻结资金, 分账6%给平台, 剩余的金额打给教练的银行卡.
    3. 如果需要退款, 直接调用退款接口即可, 资金直接从冻结池扣除，无需手动解冻
    4. 0 元订单不走微信支付, 自然也不会出发分账接口
    5. 同一订单最多允许发起 50 次分账请求, 可以部份分账或者部份退款的, 资金来源是「冻结池余额」
3. JSAPI 支付下单、退款、异步通知三套接口的幂等方案，用什么唯一键防重复回调？重复退款如何拦截？
    - 同一个请求，重复执行 N 次，产生的效果和只执行 1 次完全一样，不会多出脏数据、重复扣款、重复分账、重复发货，这个实现方案就叫幂等方案。幂等 = 重复调用无副作用。
    1. 主要是`定义一个唯一标识`
        1. 下单时
            - 后端用雪花算法生成一个唯一订单ID
            - 在微信预支付时, 会有一个微信支付单号
        2. 退款接口
            - 也是后端一个, 微信内部有一个退款id
            - 这个订单单号和退款id是绑定的, 退款时如果发现已经有退款id, 且状态不是取消, 就不允许重复发起退款
        3. 接受异步回调是一样的
4. 积分抵扣混合支付场景：支付金额拆分、退款时积分原路退回逻辑，出现部分退款怎么计算积分返还？
    - 单次课最简单, 用多少tuik多少
    - 多次课是根据学员已上课次数计算剩余可退款金额的, 同一订单最多允许发起 50 次分账请求

# 3. Redis 缓存优化、WebSocket 站内推送
1. 用户资料、粉丝、钱包聚合缓存，多表串行查改并行缓存设计；多端同时更新用户数据时缓存更新一致性怎么保证？
    1. 结构: 用户所有聚合数据统一一个根 Key，分多个 Hash 存储，避免超大 Value 序列化卡顿
        - 写场景：只修改对应 Hash，不用全量删改整个用户缓存；
        1. user:agg:{uid}, 根前缀
        2. user:agg:{uid}:base_info , Hash1, 基础资料
        3. user:agg:{uid}:wallet, 钱包信息
    2. 更新流程上: 所有修改操作强制顺序：数据库事务提交成功 → 再操作 Redis 缓存
        1. 如果需要更严格的话, 可以使用RLock lock = redissonClient.getLock(lockKey); 抢锁失败，返回繁忙，不执行缓存更新
        2. 只修改变更字段，其余缓存字段保留，适合聚合 Hash 结构,不清除整个缓存
            1. HSET base_info nick_name xxx
            2. HINCRBY wallet balance 1000；
    3. 场景 2：多端同时更新同一用户（小程序改资料 + 支付回调改钱包）
        1. 两个请求各自开启 MySQL 事务，串行更新对应表，分别自增 version；
        2. 事务都提交成功后，争抢 lock:user:agg:{uid} 分布式锁；
        3. 抢到锁的线程先执行 Lua 版本校验写入对应 Hash；
        4. 后抢到锁的线程执行 Lua 脚本时，检测缓存 version 已大于自身 DB 版本，直接放弃写入；
    4. 场景 3：异步延迟更新（分账 MQ 回调，晚于前端更新）
        1. MQ 消费更新钱包 DB，version+1；
        2. 尝试获取分布式锁失败（前端正在更新缓存）；
        3. 等待锁释放后执行 Lua 脚本；
    5. Redis总结
        1. 禁止先更缓存后更数据库，并发下必然脏数据；
        2. 单纯过期时间无法解决并发覆盖，必须搭配锁或版本号；
        3. 不要使用统一大 String 存储整个用户聚合数据，局部修改会全量覆盖；
        4. MQ 异步更新必须携带 DB 版本号，用 Lua 原子条件写入，不能直接 HSET 覆盖；
        5. 分布式锁必须加过期时间，防止服务宕机死锁阻塞用户更新。

2. 缓存淘汰、热点 key、缓存穿透 / 击穿 / 雪崩在学员高并发访问下做了哪些防护？
    1. 淘汰策略：volatile-lru
        - 只对带过期时间的缓存做 LRU 淘汰，永久 key（配置、白名单）永不清理
        - 学员缓存统一设 12h 过期，属于 volatile
    2. 热点 Key 防护（爆款课程、头部讲师、热门学员粉丝数高频访问）
        1. 埋点统计每个 key 的 10s 窗口 QPS，超过 5000 判定为热点：
        2. 对已知超高热点 key（爆款课程、头部教练），后台定时生成多份副本 key：
            - course:hot:1001:copy1, 查询时随机路由其中一个副本，分散槽位请求
    3. 缓存穿透防护（查询不存在学员 / 不存在课程，频繁打 DB）
        1. 空值缓存, 查询学员 uid 不存在时，写入短过期空 Hash：
            - user:agg:9999999:base_info 空hash，过期3min
        2. 布隆过滤器
            - 服务启动时，把所有有效学员 uid 载入 Redis 布隆过滤器
    4. 缓存击穿防护（热点 key 刚好过期，大量并发同时打 DB）
        1. 计算热点key, 设置逻辑永不过期（高热度讲师 / 爆款课程专用）
        2. 统一基础过期 12h，追加 ±0~180s 随机偏移, 避免大批量学员缓存集中同一秒过期
    5. 缓存雪崩防护（大批量 key 同时过期 / Redis 宕机，DB 瞬间压垮）
        1. 统一基础过期 12h，追加 ±0~180s 随机偏移, 避免大批量学员缓存集中同一秒过期
