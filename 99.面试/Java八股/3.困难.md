3. 高并发中的集合
    1. 第一代 Vector和Hashtable, 线程安全效率低
        - 总是用`synchronized`修饰方法
    2. 第二代 ArrayList和HashMap, 线程不安全性能好
        - 如果需要线程安全, 可以使用`Collections.synchronizedList(list)`之类的方法
        - 内部还是`synchronized`代码块, 与第三代比不灵活
    3. 第三代 CopyOnWriteArrayList和ConcurrentHashMap
        - java.util.concurrent.* 类下的集合
        - 底层使用`CNS``AQS` Lock锁
        - 既保障了线程安全, 又提高了效率

1. HashMap 在JDK8后的结构与扩容机制？并发下会怎样？
    - JDK 8 对 HashMap 做了重大优化，核心结构从 “数组 + 链表” 升级为 “数组 + 链表 + 红黑树”，目的是解决链表过长导致的查询效率低下问题。
        - 数组长度 ≥ 64 才树化
    1. 并发场景
        1. HashMap线程不安全
        2. ConcurrentHashMap, 里面所有方法都是使用`synchronized`修饰进行锁定的, 这确保了单线程运行

2. 先明确核心参数的底层逻辑（10 秒铺垫）
    - corePoolSize：核心线程数（常驻线程，不轻易销毁）；
        - CPU 核心数 + 1
    - maximumPoolSize：最大线程数（核心线程忙 + 队列满时，临时扩容的上限）；
        - 针对批处理(一次性全运行), 等于corePoolSize
    - workQueue：任务队列（核心线程忙时，暂存待执行任务）；
        - 用ArrayBlockingQueue（有界队列）, 容量设为日常任务量的 1.2 倍
        - 取决于要把数据处理拆分成多少个任务
    - keepAliveTime：非核心线程空闲超时销毁时间；
        - 由于没有非核心, 因此设为0
    - rejectedExecutionHandler：队列满 + 达到最大线程数时的拒绝策略。

3. volatile 关键字
    - volatile 关键字, 保证 volatile 变量相关的代码执行顺序和代码书写顺序一致, 禁止 JVM 对指令的乱序优化, 一般用于初始化, 避免线程 B 拿到 “未初始化完成但标记为已初始化” 的连接池，导致调用失败。
    - 如果要保证原子性的话, 一般用@Trunsaction
