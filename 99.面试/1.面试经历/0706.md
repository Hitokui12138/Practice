1. 简单介绍你的结算项目，说清楚整体流程、你负责核心模块、技术选型理由。
    1. `整个系统`分为主数据模块、批处理模块，用来运维的CMS模块
        1. 首先主数据会收集各个渠道加盟商产生的交易流水，定期上传至AWS S3分区
        2. 每日凌晨的时候 Airflow 调度触发 Spring Batch 日终批任务，按加盟商编号和拉取前一日全部 CSV 流水；
            - 在批处理内部完成数据清洗、校验，汇总，然后把结果存入数据库， 同时生成对账报表归档回 S3
        3. 运营通过CMS平台提供的接口可以查询结算明细、发起分润申请；
    2. `我负责的模块`
        1. 日终批量精算模块：Spring Batch 批处理逻辑 + MWAA Airflow 调度 DAG，包含任务依赖编排、失败重试、监控日志；
        2. CMS 平台那边有几个结算查询的编写，配套 Redis 缓存优化方案
    3. 选型理由
        1. Spring Batch：结算属于海量数据批量计算场景，框架天然支持分片、事务、分段读写，保证批量数据计算失败可回滚，适配日终大批量流水核算；
        2. Airflow + AWS MWAA：多阶段结算任务有强先后依赖（先拉文件→清洗→核算→归档），Airflow `可视化` DAG 能清晰管理依赖

2. 具体做过哪些业务
    1. 加盟商`分润利益`的结算，`服务费`的结算， 因为线下门店加盟商加入这个电子货币系统后， 按合同比例计算品牌总部与加盟商的分成，服务费
        - 主要是系统内部应收应付记账，不涉及真实跨行资金交割。
        - 分润规则可灵活配置阶梯抽成、固定服务费，规则迭代自由度高。

3. Spring Batch 完整执行流程是什么？ItemReader/ItemProcessor/ItemWriter 分别在你项目做了什么？
    1. 主要有三个Step
        1. Step1: 验证执行参数是否正确， 尝试从s3拉取数据到本地，然后验证文件md5编码是否一致
        2. Step2: 
            0. Step 先读取配置的事务、分片、提交间隔；
            1. ItemReader：逐条 / 分页读取数据源（文件、数据库）；
                - `FlatFileItemReader`
                - 增加文件分片读取逻辑，多渠道文件并行 Reader 提升速度；
            2. ItemProcessor：每条数据业务清洗、校验、计算；
                - 业务处理
            3. ItemWriter：批量攒 N 条后统一写入 DB / 文件；
                1. 采用CompositeItemWriter组合两个写入逻辑
                    1. 数据库写入（JdbcBatchItemWriter）
                    2. 报表文件写入（FlatFileItemWriter）
        3. Step3:
            1. 主要用来更新数据库中批次状态
    
4. 日终核算分多阶段，阶段之间存在执行依赖，你在 Airflow DAG 怎么配置依赖关系？
    - 一般一个DAG执行一个JOB
    - 也有少部分需要顺序执行的， 这个时候用 `>>` 指定顺序即可
    - 也可以配置重试次数等等： retries=3、retry_delay=300

5. 批任务中途失败怎么处理？重试机制是 Airflow 层面控制还是 Spring Batch 内部做的？断点续跑怎么实现？
    1. 失败要分情况
        1. S3 文件拉取超时， 参数错误之类的会判定整个JOB失败，此时AirFlow会根据DAG文件的配置隔一段时间后重试
            - 等待5分钟， 重试3次
        2. 数据库更新失败，通过 RetryTemplate、SkipPolicy 实现：单条记录失败只回滚当前 chunk，不会中断整个批任务，脏数据记录日志跳过，正常数据继续执行。
            - FlatFileItemReader，执行时会记录文件读取行号，任务崩溃重启后，Reader 直接从上次失败的行开始读取

6. 如何避免OOM? Chunk是怎么设计的
    1. Spring Batch 本身不是一次性读取所有数据到内存，核心靠`分块 Chunk` 机制隔离内存
        - 内存常驻数据永远只有 1 个 chunk 的对象，不会累积全量流水
    2. 我们这个项目的chunkSize是1000， 上游的文件也是如果超过10万条，会分成两个文件
        - 事务边界：依然按 chunk=1000 提交，跨文件不会破坏事务逻辑
        - `MultiResourceItemReader`,外层包装，遍历所有文件资源
        - `FlatFileItemReader`, 真正解析单个文件，你的原有文件读取逻辑不动
    3. 单 CSV 超百万行时，分区器读取文件总行数，按固定行数切割分片，例如每 10 万行一个分片；每个分片记录 startLine、endLine，Reader 读取时直接跳过前面行，只处理当前分片区间数据。
        - FlatFileItemReader支持linesToSkip配置，分片启动时直接跳到起始行，不用逐行遍历前置数据。
    4. 我们这个批处理属于是离线批处理，对速度要求没那么大

7. Airflow 调度任务重复触发（服务重启、定时重复执行），怎么保证结算不会重复计算（幂等方案） `幂等方案`
    1. 首先Airflow调度层max_active_runs=1，禁止同一结算日期并发 执行DAG的；
    1. 我们有自定义一个JOB执行情况表， JOB开始执行时， 会按`Batch编号+加盟商编号+执行日期还有一个执行状态`作为唯一幂等键， 当执行状态不为失败的情况下， 是不允许重复执行的

8. 批任务监控日志怎么收集？任务失败如何告警？
    1. 统一日志框架：Log4j2，标准 JSON 日志， 里面会有batchDate、partition、fileName之类的
    2. AWS提供一个叫CloudWatch的功能， 给云端的虚拟主机安装一个插件amazon-cloudwatch-agent，定时扫描日志文件，批量推送到 CloudWatch LogGroup。
