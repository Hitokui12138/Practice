## Spring
1. IoC (Inversion of Control:控制反转)
    - 是一种思想不是一个技术实现, 不通过 new 关键字来创建对象，而是通过 Spring 框架提供的IoC 容器来帮助我们实例化对象
    - 不通过 new 关键字来创建对象，而是通过 IoC 容器(Spring 框架) 来帮助我们实例化对象。我们需要哪个对象，直接从 IoC 容器里面去取即可。
    - 控制： 指new一个对象的能力； 反转： 指将这个能力给IoC容器
    - 对象之间的耦合度或者说依赖程度降低；
    - Bean 代指的就是那些被 IoC 容器所管理的对象
2. @SpringBootApplication
    1. @Configuration
    2. @EnableAutoConfiguration，开启自动配置
    3. @ComponentScan,扫描项目中其他配置类
3. AOP，面向切面编程，把打印log等等操作给封装起来，在业务方法调用前后自动调用
    - @Aspect 定义一个切面类
    - @PointCut 定义切入点
    - @Around，@Before，@After
4. Spring事务
    1. 通过声明式事务`@Transactional`注解标记`方法/类` 
        - 参数：什么异常回滚，不回滚，传播行为，隔离级别
    2. 传播行为(上面一个方法，下面一个方法)
        1. `REQUIRED` (默认)，有事务则加入，无则新建
            - 普通业务方法, 下单(主事务)+扣除库存(子事务), 要么都成功,要么都失败
        2. `REQUIRES_NEW`
            - 无论是否有事务，都新建独立事务（新事务与外层事务隔离）
            - 日志记录、消息发送(当主事务回滚时, 日志不随着一起回滚)
        3. `SUPPORTS` 有事务则加入，无则以非事务执行
            - 下单（事务）后查订单（加入事务）， 直接查订单（无事务）
        4. `NOT_SUPPORTS`以非事务执行，有事务则挂起
            - 调用第三方接口时， 先让事务挂起等待， 不要占用太多数据库联结
    3. 隔离级别
        1. 数据库的三大问题
            - READ_UNCOMMITTED，`读未提交`
            1. 脏读，读到了其他事务未提交的数据
            - READ_COMMITTED，`读已提交`
            2. 不可重复读，其他事务提交后数据变了
            - REPEATABLE_READ，`可重复读，mysql默认`
            3. 幻读，其他事务提交后数据的行数变了
            - SERIALIZABLE，`串行`
        2. 一般用Default，或者SERIALIZABLE（串行）
            - mysql的默认是可重复读级别，解决了脏读和不可重复读的问题
    4. 事务回滚的条件
        - 远吗默认配置： `@Transactional(rollbackFor = RuntimeException.class, Error.class)`
        1. 自动回滚：
            - 默认情况下方法`抛出` RuntimeException（运行时异常）才`自动回滚`
            - 如果需要自定义异常回滚， 需要设置成`@Transactional(rollbackFor = Exception.class)`
                - 让所有异常都回滚
        2. 手动回滚
            - 在没有抛出异常，仅用catch代码块的情况下
                1. `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();`
                2. `transactionTemplate.execute(status.setRollbackOnly())`
            - 代码执行后，会根据Status的值判断是否回滚
    5. 事务失效
        - Spring 事务靠 AOP 动态代理实现
        1. 同类内 this.xxx () 直接调用，不走代理，事务完全失效。
        2. Spring AOP 只会拦截 public 方法，其他会失效
        3. 异常被 try-catch 捕获，没有重新抛出，必须抛出才能触发自动回滚
        4. 抛出受检异常（Exception）但未配置 rollbackFor
            - Spring 默认只回滚运行时异常 RuntimeException
        5. 传播行为配置错误
        6. 新开子线程执行 DB 操作，不在原事务内，互不影响
    6. 场景题
        1. 防止超卖
            1. 扣减商品库存、生成支付单在同一个事务中，传播行为 REQUIRED
            2. 隔离级别默认 REPEATABLE_READ， MySQL默认的`可重复读`
            3. 库存扣减使用`SELECT ... FOR UPDATE`行锁，避免并发超卖，数据库悲观锁
        2. 分账接口是第三方API（就说没做过吧）
            1. 分账接口
                1. 分账主接口：调用是同步受理，但不会立即返回执行结果
                2. 有回调通知，但是不通知平台，而是通知商户
                3. 唯一方法： 主动轮询查询接口，查询分账结果 API
            - 完成订单 -》 调用分账接口 -〉本地生成分账流水、商户待结算余额。
            1. 使用本地消息表和MQ实现`最终一致性`
                1. 发起分账时，在本地事务中更新课程状态表，更新分账记录表
                2. 独立定时任务轮询本地消息表，如果有状态为pending的记录，就
                3. 如果消息表有消息，就驱动MQ 消费端执行分账逻辑

## Mysql
1. 加索引
    1. 无索引时：全表扫描
    2. 索引本质：有序的 B + 树结构
2. B+树
    - 所有的数据全部放在叶子节点上, 根结点只存放指向其他节点的指针
    - 整个树更加扁平, 减少IO次数
3. 优化方案
    1. 加索引
        1. 优先选择区分度高的字段建索引
        2. 查询语句中，where 条件必须命中最左前列
        3. 不要使用 like '%关键词' ，not null否定查询 会使索引失效
    2. SQL优化
        1. 不要用select *
        2. 用explain分析sql，不要全盘扫描
    3. 分库分表
        1. 单表行数超 500W~1000W
            1. 水平分表，按数量级分成多个相同的表
            2. 垂直分表，将一个user表拆分成多个表
    4. 读写分离：主库写入，从库查询，分摊读压力
    5. 使用缓存，减少数据库查询次手

## RabbitMQ
1. 生产者把消息发到交换器（Exchange），交换器按照绑定规则把消息路由到队列（Queue），消费者再从队列取走消息。
2. DLX，全称为 Dead-Letter-Exchange（死信交换器），
    - 当消息在一个队列中变成死信（dead message）之后，它能被重新发送到另一个交换器中，这个交换器就是 DLX，绑定 DLX 的队列就称之为死信队列。
3. 延迟队列
    1. 使用 TTL + DLX。消息先进入`带 TTL 的队列`，过期后被投递到`死信交换器`
    2. `死信交换器`把这条消息发送到`真正消费队列`
4. 消息队列可靠性
    1. `生产者`向消息代理传递消息的过程中，消息丢失了
        - 生产者重连机制，投递后确认机制
    2. `消息代理`（ RabbitMQ ）把消息弄丢了
        - 对队列，消息进行持久话保存
    3. `消费者`把消息弄丢了
        - 消费者确认机制，处理失败的消息失败重试机制，保存失败消息的机制
    4. 给每条消息都设一个id
