# 网络编程
- 让两台计算机通过网络互相收发数据的编程技术。
1. 核心概念
    1. IP地址, 定位一台设备
    2. 端口 Port, 定位设备上的某个程序
    3. 套接字 Socket, 
2. 最核心的两个协议
    1. TCP (打电话, 可靠)
    2. UDP (寄信, 快，但可能丢包)
3. IO模型(重点)
    1. 阻塞IO
        - 来一个连接开一个线程，并发差。
    2. 非阻塞IO
        - 轮询，浪费 CPU。
    3. IO多路复用
        - 一个线程监听成千上万个连接
    4. 信号驱动 IO / AIO (用得少)
4. 高并发网络编程的进化路线
    1. 多进程 / 多线程
    2. 线程池
    3. IO 多路复用 + 事件循环（`Reactor 模型`）
        - Nginx、Redis、Go、Netty 都用这个
            - Go 的 goroutine + 底层 IO 多路复用 = 天然高并发。
## Socket 套接字
- 应用层 和 传输层之间的`接口`, 本质是编程接口（API），
- 程序与网络之间的「双向通信接口」, 调用它的 API 就能让程序收发网络数据，不用关心底层的 TCP/UDP、网卡、网线这些细节。
- `Socket的五元组`记录了`本地 IP + 本地端口 + 远端 IP + 远端端口 + 协议`这 5 个核心信息，用来唯一标识一个网络连接。
1. 一个打电话的例子
    1. Socket是能收发网络数据的接口, 也就是`电话`
    2. 你的手机号(本地IP+端口) 127.0.0.1:8080
    3. 对方手机号(远端UP+端口) 192.168.1.100:9000
    4. 拨号, 客户端调用`connect()`
    5. 接听, 服务端调用`accept()`
    6. 说话/听 `send()/recv()`
    7. 挂断(关闭Socket), 调用`close()`
2. Socket 服务器 = 运行在服务器上、通过 Socket 接口监听网络端口、接收并处理客户端连接 / 数据的程序
    - 写网络程序时，最核心、最基础的服务端载体

## TCP
- TCP 是一个可靠、面向连接、基于字节流的传输层协议
1. 三大特点
    1. 面向连接
        - 通讯前必须先`建立连接`, 通讯完必须`断开`
    2. 可靠传输
        - 不丢包, 不乱序, 不重复
    3. 面向字节流
        - 数据像水流一样发出去，没有明显边界 → 所以会有`粘包问题`。
2. 三次握手, 四次挥手
    1. (建立连接时)三次握手
        1. 打电话
            1. C->S: 能听到吗? (SYN)
            2. S->C: 能听到, 你能听到我吗? (SYN + ACK)
            3. C->S: 听得到, 建立连接! (ACK)
        2. 可见`至少要 3 次`才能双向确认收发都正常
    2. (断开连接时)四次挥手
        1. 挂电话
            1. C->S: 我说完了, 想挂电话了. (FIN)
            2. S->C: 知道了, 我还没说完,等我一下.(ACK)
            3. S->C: 我也说完了, 挂电话吧.(FIN)
            4. C->S: 拜拜, 断开连接.(ACK)
        2. 双方可能还在发数据，不能说断就断。
3. 如何确保可靠性
    1. 序列号 + 确认应答（ACK）
        - 发一段数据，对方必须回 “收到了”。
    2. 超时重发
        - 没收到 ACK，就重新发
    3. 流量控制
        - 对方收不过来时，放慢发送速度，防止丢包。
    4. 拥塞控制
        - 网络堵了，就放慢发送，防止丢包。
4. TCP 粘包 / 拆包
    - 由于TCP 是字节流，没有消息边界。
    - 因此发送`hello world`, 对方可能收到:
        - `helloworld` ,粘包
        - `hel world` ,拆包
    1. 解决方案
        1. 固定长度, 或者分隔符
        2. 消息头 + 消息体
            1. 消息头: 核心信息是`消息体的总长度`
            2. 消息体: 真正要传输的业务数据
                - 这样接收方能精准读取对应长度的包体 → 刚好拿到完整的一条消息，彻底解决粘包 / 拆包。
