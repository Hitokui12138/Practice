# 软件架构
- 将系统分成不同的部分, 选择特定的技术
1. 考虑因素
    1. 业务需求
    2. 公司的技术栈
    3. 成本
    4. 公司的组织架构
    5. 可拓展性
    6. 可维护性(新人的学习成本, BUG修复成本)
2. 软件架构的进化
    1. 一层架构
        1. JSP里面有HTML,JAVA代码
        2. 一个方法好几百行
    2. MVC, SSH, SSM
        1. 三层架构
        2. 通过接口, 将各个模块进行分离
        3. 分工明确
    3. dubbo? 分离前后端? 但还是单体架构
3. 单体架构, 单块架构
    1. 虽然分了层, 但是功能和业务仍集中在一个发布包里, 部署在同一个进程
    1. 优点
        1. 易于开发, eclipse和Idea也很适合单块架构
        2. 易于测试, 所有功能都在这里
        3. 易于部署, 就一个包
        4. 易于水平伸缩, 即通过增加节点来复制
    2. 缺点
        1. 代码膨胀, 难以维护, 修复一个BUG可能引入新的BUG
        2. 构建, 部署, 持续交付周期长
        3. 新人上手困难, 
        4. 创新困难, 传统项目一般使用统一的前后端技术
        5. 可拓展性差
            1. 垂直拓展
                1. 程序运行在一台机器上,加多少内存?多少CPU?
            2. 水平拓展
                1. 有的功能对内存要求高,有的对CPU计算要求高
4. 微服务
    1. 使用一套小服务来开发单个应用
        1. 每个服务运行在`独立的进程`里
        2. 采用`轻量级通讯机制`来互联
        3. 可以通过`自动化`的方式进行部署
    2. 怎样算微服务?
        1. 代码量?小于10000行?(不靠谱)
            1. 假如一个算法需要很多内存操作
                1. java和c++需要的行数区别很大(语言的区别)
            2. 人的区别
        2. 这个微是不可度量的, 不是一个固定的量
    3. 但是有一些特征
        1. 单一职责 
            1. 订单和支付可以做成一个微服务
            2. 登录和注册可以作为一个单独服务
            3. 邮件之类的与其他业务相关性小的服务
        2. 轻量级通讯机制
            1. 与平台无关, 与语言无关的通讯协议
                - 比如http
            2. 举几个不轻量的
                - java的rmi, .net的remoted
            3. 隔离性,相互不干扰
            4. 有自己的数据存储系统
            5. 技术多样性, 开发者可以选择合适的语言
    4. 微服务的出现离不开
        1. 互联网技术发展
        2. 敏捷开发, 需要频繁交付,改需求
        3. 容器技术的成熟, 解决了运维环节
