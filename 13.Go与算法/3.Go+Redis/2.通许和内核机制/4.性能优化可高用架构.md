# 性能优化
- Redis很快,但你的代码可能很慢
- Pipeline, lua, 线程池设计
- 主从复制, Sentinel, Cluster 三种高可用框架
- 理解缓存雪崩, 击穿, 穿透 
- 用Pipeline优化接口性能进行压测对比
## 一. Redis很快,但你的代码可能很慢
1. 问题
    1. 假设有一千条命令, 那么就有一千次`RTT`(网络往返)
        - 使用`pipeline`, 减少RTT
        - 使用`lua脚本`, 原子操作
    2. 连接频繁创建销毁
        - 使用连接池
## 二.Pipeline
1. 什么是RTT(Round Trip Time), 请求往返的时间
    - 一次请求延迟约 0.5~2 毫秒(内网), 累计后很大
2. Pipeline原理
    - 把多个独立的请求 / 命令批量打包，通过一次网络传输发送到服务端，服务端批量处理后，再通过一次网络传输返回所有结果。
    - 一次RTT完成多个命令
3. 使用场景 (简单的, 吞吐高的)
    1. 批量写入(初始化数据, 批量更新)
    2. 批量查询(MGET替代多次GET)
    3. 非关联的多条命令
4. Pipeline不适合
    1. 命令之间有关联性(比如后一条需要前一条的结果)
    2. 需要事务一致性的命令
## 三. LUA脚本
1. 对于有依赖关系的命令
    1. GET 库存
    2. 判断 > 0
    3. DECR 库存
2. LUA可以`打包`上面三条命令, 在Redis里面`原子执行`
    - 把整个脚本作为一个原子来执行
    - 阻塞Redis主线程, 确保LUA执行期间其他都不执行
    - 脚本也会缓存在Redis中, 可以复用
3. 对于更复杂的事务
    - 需要LUA与reconsider结合使用
## 四. 连接池
1. go-redis 可以直接解决这个问题
    - 全局复用一个Client (线程安全)
    - 不需要频繁创建和关闭
    - 根据QPS调整PoolSize

# 高可用架构
1. 单机有很多问题
    1. 机器宕机后服务不可用
    2. 数据丢失无法恢复
    3. 容量有上限, 内存有限
2. 解决方案的演化
    1. 主从复制
        - 读写分离, 写主节点, 读分节点
    2. Sentinel 哨兵模式
        - 监控, 通知, 自动故障转移
    3. Cluster, 集群模式
        - 多个主节点
## 一. 主从复制
- 通过配置文件启动
- 向Master节点进行写操作, 向Slave节点进行读操作
- 读写分离
- 异步同步, 很快, 有一点点延迟
1. 复制数据的过程   
    1. Slave节点上线后, Master节点将`RDB文件`发给他让他初始化
    2. 复制是异步的, 有些延迟
2. 如果Master宕机, 需要手动切换节点

## Sentinel 哨兵模式
- 解决了手动切换的问题
- 作为一个第三方, 既能监控主节点, 也能监控从节点
1. 主要作用
    1. 监控
    2. 通知, 通知客户端让他换一个节点
    3. 自动故障转移, 选举新节点, 然后把新的主节点地址给客户端
2. 需要用Go连一下Sentinel
    - 而且需要连接多个哨兵, 因为哨兵节点本身也可能会宕机

## Cluster集群模式
- 彻底解决单机容量上限问题
1. 多个主从结构
    - Master ABC 分别负责`不同的数据分片`
    - 比如A负责0~5460槽位, B负责5461~10922槽位
2. Go
    - 通过指定多个地址, 来指定不同的主从结构
## 如何选择三种架构
1. 数据量<10GB,  主从复制+哨兵模式即可
2. 数据量>10GB或者有水平拓展需求时, 使用Cluster进行高并发

# 缓存的三大问题(都是绕过缓存查崩数据库)
1. 缓存雪崩(Avalanche)
    1. 原因
        1. 同一时间, `一批大量缓存`过期
            - 查询5000个ID都没有
        2. 请求全部打到数据库
        3. 导致数据库宕机
    2. 防御
        1. 给过期时间加一个随机值
        2. 热点数据永不过期, 或者主动更新
        3. 多级缓存(Redis + LocalCache)
        4. 熔断降级, 数据库压力大的话就直接返回默认值
2. 缓存击穿(Breakdown)
    - 热点事件, 秒杀商品
    1. 原因
        1. 有一个热点`KEY`, 突然过期了
        2. 缓存没挡住，大量请求同时查询数据库
        3. 数据库宕机
    2. 解决
        1. `分布式锁` 
            - 不要所有请求都去查数据库, 只要有一个请求就行
                - 拿不到锁就等待
            - 拿到锁的线程查询数据库, 然后更新Redis
        2. 热点数据永不过期
            - 缺点在于缓存会一直增大, 终有一天会崩溃
3. 缓存穿透(Penetration)
- 恶意攻击：用大量不存在的 ID 刷接口, 查询一个`不存在的数据`, Redis没有, 因此都去查数据库, 从出现大量无效请求
    1. 防御
        1. 布隆过滤器(推荐) Bloom Filter
        2. 缓存空值
            - 查询数据库, 若数据库内也没有, 则在Redis中设置一个短有效期的空值
        3. 做参数校验
