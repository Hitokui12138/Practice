# 短信登录
## 工作流程
### 1. 发送验证码给用户 
1. 用户提交手机号
    1. 验证手机号格式
2. 生成验证码
    1. 验证码保存到`Session`中 (传统)
        - 现在包存在Redis当中, 以手机号为Key
        - `phone:18917409723 | 验证码` 
    2. 发送短信给用户
### 2. 短信验证码登录, 注册
1. 验证 验证码
    1. 从Session中取得验证码 进行比较
2. 根据手机号查询用户信息
    1. 用户存在 -》 登录
    2. 用户不存在 -》 注册
3. 将用户保存在Session里
### 3. 校验登录状态
0. Session知识
    - Session是基于Cookie的, SessionId包存在Cookie当中
1. 用户携带cookie发起请求
    1. APP从Session中取得Id
2. 判断用户是否存在
    1. 不存在: 拦截
    2. 存在: 保存用户到ThreadLocal中

### Session验证登录是否可行?
- Session适合服务端渲染（如 Spring MVC+JSP/Thymeleaf）的场景；但如果是前后端分离项目，更推荐 Token（如 JWT）方案
#### Session流程
1. HttpServletRequest.getSession()
2. 用拦截器验证`Session`里面是否有登录信息
3. 注册拦截器?让拦截器生效
#### JWT流程
1. JWT工具类
2. login()方法生成token, 返回
3. 拦截器拦截验证`请求头`是否有token
4. 也需要注册拦截器等等操作
5. JWT的优点:
    1. 服务端不需要存储Session数据
        - 服务端只需通过算法校验合法性，无需内存 / Redis 存储
    2. 分布式/微服务时, 不需要做 Session 共享（Redis）
    3. 不依赖 Cookie，适配所有端
        1. JWT,通过`请求头 / 参数`传递, 适配多端
        2. Session, 依赖 Cookie 传递 JSESSIONID, 移动端没有Cookie机制
    4. 天然支持单点登录(SSO)
        - 一个系统生成的 JWT 可被其他系统直接校验
        - Session则需要开发单点登录, 然后多系统共享Session信息
    5. 可嵌入业务信息
        - JWT 的载荷（Payload）可嵌入非敏感业务信息（如用户 ID、角色、权限）
        - Session 仅存用户标识, 需要再查询数据库
6. JWT缺点
    1. 无法主动失效, 可以结合`Redis的黑名单`功能, 踢出一个用户
