# 分布式锁 与 RedLock
## 一. 为什么要用分布式锁
1. 单机锁的局限性
    1. 单机锁只在当前进程有效
    2. 微服务`多实例部署`时, 单机锁无法跨进程同步
    ```go
    var mu sync.Mutex
    func process(){
        mu.lock()
        defer mu.Unlock()
    }
    ```
    3. 需要一个公共逻辑来控制到底哪个实例能操作(这就是分布式锁)
2. 分布式锁的要求
    1. 互斥性, 任意时刻只有一个客户端能获得锁
    2. 防死锁, 锁要有过期时间, 也要有续期的方法(看门狗)
    3. 高可用, 锁服务不能出现单点故障

## 二. Redis的单节点锁
1. 核心命令
    - `SET resource my_random_value NX PX 30000`
    - `SET k v NX PX time`
    - 尝试给名为 resource 的 key 设置值为 my_random_value，仅当该 key 不存在时才设置成功（NX），并给这个 key 设置 30 秒的过期时间（PX 30000）
    1. 互斥性: NX, 仅当Key不存在时才能设置成功
    2. 防死锁: PX 30000, 设置过期时间
    3. my_random_value: 唯一标识, 释放时验证身份
2. 解锁时需要使用LUA脚本    
    1. 判断锁值匹配
    2. 然后删除这个锁


# 多节点的情况下    
## 三.Redlock算法(不推荐)
- 当我有多个Redis节点的时候
1. Redlock算法
    1. 在N个独立的Redis节点上同时`尝试获取锁`
    2. 成功节点 > N/2 + 1, 且 < 过期时间, 才算成功
2. 优点
    - 这样的好处是可以容忍少量故障节点
3. 缺点
    - 算法要求你的节点数量必须是奇数
    1. 这样的算法非常麻烦, 你需要让`客户端`分别轮询所有的Redis节点才能实现

## 四.强一致性需求: 使用etcd
- 但etcd性能远远比不上redis
1. Redlock vs etcd
    1. Redlock
        1. 最终一致性(AP)
        2. 实现复杂性高, 需要客户端实现这套算法
        3. 可靠性有争议
    2. etcd
        1. 强一致性(CP)
        2. 复杂度低, etcd服务端就能保证
        3. 可靠性严格遵循Raft协议
2. 因此建议金融交易,库存扣减等强一致性的场景使用`etcd`
