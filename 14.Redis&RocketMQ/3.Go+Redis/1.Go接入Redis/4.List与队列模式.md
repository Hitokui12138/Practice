## 一. Redis的List不是传统的数组
1. Redis的List是`有序可重复的序列` (支持头尾操作)
    1. 左右插入, 左右弹出, 阻塞读取, 范围读取
2. 典型用途:
    1. 队列
    2. 最新动态
    3. 异步任务
## 二. List底层结构 QuickList
- redis的List`不是数组`, 也`不是传统链表`
1. QuickList结构
    - 一个QuickList包含多个listpack,listpack里面存着多个`内存大概率连续的`元素
    - listpack(类似于ZipList) [k1|v1|k2|v2|k3|v3]
    - listpack
2. 优势
    1. 使用listpack, `连续内存`, CPU缓存友好, 减少使用指针
        - 因为连续内存, 因此不需要new()
    2. 链式连接, 支持快速插入, 插入效率稳定, 避免整体移动
        - 满了就新建一个listpack
## 三. List操作
1. `LPUSH`,`RPUSH`
2. `LPOP`,`RPOP`
3. `LLEN`, 返回长度
4. `LRANGE`, 遍历输出, 不要设置过大范围, `-1`可以表示队尾

## 五. 阻塞队列
- 让生产者一直写入, 消费者隔一段时间POP一次
1. `轮询`对CPU消费过高,而且延迟也很高
    ```
    while true {
        RPOP
        sleep //隔一段时间轮询一次
    }
    ```
2. Redis提供`BLPOP`方法, `没有数据就等待`
    - 几乎是零轮询, 实时消费, CPU友好
    - `BLPOP queue 0`
    - 拿到job后就立即退出了
    ```cli
    // 终端1:
    LPUSH task_queue job1
    LPUSH task_queue job2
    // 新终端2:
    RPOP task_queue
    // 阻塞
    BLPOP queue 0
    // 终端1:
    LPUSH task_queue job3
    ```

## 七: Redis的List的缺陷, 与专业MQ的区别
1. 缺陷
    1. 无确认机制
        - POP之后, 不知道是否消费成功, 不知道对方有没有收到
    2. 无重试机制
        - POP之后, 即使发现出了错, 也没办法让Redis重试
    3. 无持久消费点位
        - 不会记录某个消费点位
    4. 无多消费者组
        - 一个消费者用掉之后, 其他消费者就拿不到了
2. 什么时候必须使用MQ?(不能忍受消息丢失)
    1. 金融交易, 订单系统 等等强一致性任务
    2. 跨服务的复杂编排
3. Redis List
    - 轻量任务, 做个定时器
    - 日志处理等等非关键任务
