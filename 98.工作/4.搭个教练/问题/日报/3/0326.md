## 今日完成
1. 订单超时不取消问题
    1. 修改前： 
        1. “自动关超时订单”只覆盖了有预约锁记录的订单，不是全量 PENDING 订单。
            - 查询条件是 booking_records.status=LOCKED + orders.status=PENDING
    2. 修改后
        1. 没有预约锁，直接把订单从 PENDING 改为 CANCELLED
        2. 有预约锁，按当前的逻辑，把超时且仍是 LOCKED 的预约记录改为 CANCELLED，同时把对应订单从 PENDING 改为 CANCELLED
2. 钱包签名问题（自动结课失败）
    1. 结算流程去掉了中途二次验签冲突（结课时在这里报错）
        - 改之前：先改 pending，再调用会先验签的方法，导致同一事务里签名按两个状态反复校验，Expected/Actual 来回翻。
        - 改之后：改成“前置验签一次 + 末尾统一更新签名一次”，不再在中间状态触发二次验签。
    2. pending -> available 的资金流转改为原子处理
        - 改之前：completePendingTransaction 和 settleCourseLessonIncome 都是“先改 pending，再走 updateWalletBalance（内含验签）”。
        - 改之后：两处都改成“内存里完成 pending/available/手续费变更 → 更新流水 → 最后一次签名并保存”。
3. 预约组设置逻辑更新
    1. 新增预约组 api/bookings/track-settings POST
        - 现在可以同时存在一组可预约时间和一组不可预约时间
        1. 新增一个可约组，则失效其他可约组，不管其他不可约组
        2. 新增一个不可约组，则失效其他不可约组，不管其他可约组
    2. 获取可预约时间 /api/bookings/track-settings/user-availability
        - /api/bookings/availability/info/2026-03-27
        - 总是返回48个时间槽
            - 1 可约， 2 不可约， 3 已约（BOOKED/LOCKED 覆盖）
        - 最终可约时间 = 全部可选时间段 − 不可约时间段
        1. 计算逻辑
            1. 若没有可用组，则返回48个不可约(2)时间槽
            2. 若只有“不可约组”，则先把整天设为可约，然后逐条覆盖： type=2 => 对区间置为不可约
            3. 若只有“可约组”，则先把整天设为不可约，然后逐条覆盖： type=1 => 对区间置为可约
            4. 同时有“可约组”和“不可约组”，先把整天设为不可约，然后逐条覆盖
        2. 当天已过去时段剔除， status为 2不可约（不能修改过去时间的可预约状态）
        3. `booking_records` 中 BOOKED(3) / LOCKED(5) 冲突剔除
            - status 设为 3已约
        4. （未实现）把booking_records中 OK(1)的slot追加到返回可用列表里
            - 想实现这个的话还需要再加一个更新`booking_records`的status为 OK(1) 的接口
4. 允许反复进出同一个团
    1. 可入团状态修改：
        - “是否在团内”的判断统一改为只看活跃记录 refundStatus = NONE，只有此时禁止重复入团；
        - PENDING/SUCCESS/FAILED （无论退款有没有成功）都允许再次入团。
