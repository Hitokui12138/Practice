# 这是一个社交媒体典型的复杂接口
1. 问题
    1. user/my 接口要一次查 6 张表， 属于高依赖，应该设短TTL 30s
        - 关注 / 粉丝 / 好友 / 访客 经常变动， 希望数据尽量实时
    2. 数量统计涉及COUNT（）， 属于慢查询， 统计数据应当使用长TTL 60min
    2. 但是短TTL，命中率极低，长TTL 更新不及时
2. 你的接口不能用 30s 短缓存，也不能用 10 分钟长缓存。
    - 正确方案是：计数实时写 Redis，不存 DB，读直接读 Redis。
    1. 计数器 不需要 TTL，（永久有效，重启恢复也不会丢）
        - DB 只做持久化，不做数据统计
    2. 用户资料， 给10minTTL

3. 最终理想方案
    user/my 接口执行流程：
    1. 从 Redis 取 6 个计数值 → 1ms
    2. 从 Redis 取用户资料（头像、昵称）→ 1ms
    3. 直接返回
    4. 全程不查 DB
    5. 接口耗时 2~6ms

4. 需要实现
    1. Redis 计数器工具类（可直接复制）
    2. 关注 / 取关时自动增减计数的代码
    3. user/my 接口全新优化版代码
    4. 零 SQL、超快返回





# 缓慢原因
1. 缓存TTL短， 只有30s
2. 落库查了7次
    - 落库链路是串行多查询：src/main/java/com/dgjl/skillup/service/impl/UserMySummaryService.java:50 起，至少 7 次查询（用户、3个关系count、访客count、积分、钱包）。
3. COUNT(DISTINCT) 可能是主要 SQL 热点：countDistinctVisitorsByVisitedId 在大表上可能慢；当前迁移里没看到 (visited_id, visitor_id) 这种直击该查询的索引。
    - COUNT(DISTINCT) 这种慢查询

# 解决
user/my 接口
1. 从 Redis 取用户基本资料（10min TTL）
2. 直接从 Redis 取 3 个实时计数：
   - su:rel:friend:count:u{userId}
   - su:rel:following:count:u{userId}
   - su:rel:follower:count:u{userId}
3. 组合后直接返回
