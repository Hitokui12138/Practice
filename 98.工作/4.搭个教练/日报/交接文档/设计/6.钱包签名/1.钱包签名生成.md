# 签名逻辑
signature = SHA256(userId + availableBalance + pendingSingleCourse + pendingMultiCourse + version + secretKey)
1. userId
2. availableBalance
    - 统一格式化到 2 位小数
3. pendingSingleCourse
    - 单次课待入账金额（还没结算到可用余额）。
4. pendingMultiCourse：
    - 多次课待入账金额（分次结算场景里还没入可用余额）。
    - 用户付款后，这部分钱先记到“待入账”（平台托管/待完成状态），不是老师立刻可提现的钱。
    - 课程完成到某一步时，再从 pending 转到 availableBalance（可用余额），并扣技术服务费。
    - 所以 pending 本质是“未最终结算”的收入池。
5. version
6. secretKey
    - 密钥来自配置 wallet.secret-key


# 金额计算逻辑
在你这段结算逻辑里就是这么流转的：

先找一笔 PENDING 的课程收入流水。
从对应 pending（单次或多次）里减掉这笔金额。
同额加到 availableBalance。
再扣 6% 服务费。

# 验证逻辑
1. verifyWalletSignature(wallet) 会重新计算一次当前钱包对象的签名（WalletServiceImpl.java:193）。
    - 计算用的是当前对象里的字段值（含当前 version），通过 generateWalletSignature(...)（WalletServiceImpl.java:154）。
2. 如果与数据库读出的 wallet.signature 不一致，就打你看到的日志：
    - Expected = 代码重算出来的值（calculatedSign）
    - Actual = 数据库里这条记录的 signature
    - （日志位置 WalletServiceImpl.java:205）
3. 什么时候会更新签名：

新建钱包时，按 version=0 生成签名（WalletServiceImpl.java:251）。
余额或待入账变更前后，代码会“预测下一版 version”来生成新签名：nextVersion = currentVersion + 1（WalletServiceImpl.java:225、WalletServiceImpl.java:315）。
然后依赖 JPA @Version 真正把 version+1 落库（src/main/java/com/dgjl/skillup/entity/Wallet.java:54）。

## 修改数据库后，对调问题
1) 读钱包
   wallet = getOrCreateWallet(userId)
   -> verifyWalletSignature(wallet)

   这里校验的状态是 S0：
   S0 = (available=A, pending=P, version=V)
   期望签名 = Sign(S0) = 7c86...   (你 10:28 的 Expected)

2) 修改 pending（尚未更新 signature）
   wallet.pending = P - tx.amount

   当前内存状态变成 S1：
   S1 = (available=A, pending=P-tx, version=V)
   但 wallet.signature 还是旧的 Sign(S0)

3) 继续 updateWalletBalance(wallet, +tx.amount)
   -> 先 verifyWalletSignature(wallet)   // 第二次校验

   这里校验的状态是 S1：
   期望签名 = Sign(S1) = de912...       (你之前日志里的 Expected)
   实际签名 = 旧 Sign(S0) = 7c86...

   => 不一致，抛 SecurityException

1. Expected=7c86, Actual=de912：失败发生在 getOrCreateWallet 这次校验（还没改 pending，状态 S0）。
见 logs/skillup.log:7078。
2. Expected=de912, Actual=7c86：失败发生在 updateWalletBalance 的校验（pending 已改，状态 S1）。
见旧栈 WalletServiceImpl.updateWalletBalance 路径。
- 所以 Expected 是真的“当下状态的期待值”，只是当下状态不同，就会出现两组哈希互相打架。
