1. 用户上传媒体审核流程更新
    1. 分别在 用户更新个人资料， 发布动态， 发布课程时读取媒体审核结果
        1. 若没有通过， 直接拒绝用户更新/发布该内容
        2. 若尚未接收到审核结果，先允许用户发布，并发布一个10秒的延迟消息
    2. 10秒后，再次读取审核结果
        1. 超时/审核未通过， 直接下架动态课程，或是把用户头像改成默认的，并通过WebSocket给用户发送消息
            - 你的动态媒体审核未通过，动态已设为仅自己可见
            - 你的课程媒体审核未通过，课程已自动下架
            - 你的头像/背景图未通过审核，请重新上传
        2. 若通过则放行
 
2. 接口性能优化 /api/users/info/{userId}
    0. 修改前
        - 该API最多查询十余次数据库
        - 修改后：优先从redis中获取
    1. 重构了缓存模型，从“单一大对象”改为分层缓存，降低缓存体积和失效抖动
        1. base：su:user:profile:base:u{userId}（基础信息，中高频变更）
        2. view：su:user:profile:view:u{userId}（展示信息，中频变更）
        3. rating：su:user:profile:rating:u{userId}（评分信息，高频变更）
        4. cert：su:user:profile:cert:u{userId}（认证信息，低频变更）
    2. 接口读取链路改为“分段读取 + 按需回源”
        1. /api/users/info/{userId} 先读上述 4 组 Redis key
        2. 某一组 miss 时，仅回源该组数据并回填缓存
        3. 最终拼装返回 UserInfoSlimVO，避免每次全链路回库
    3. 对于COUNT（）等慢查询进行聚合
        - 原先 count/sum/latest/users/orders 多次访问 DB的各个表
        - 现在通过一条聚合 SQL（CTE + 窗口函数）一次拿齐评分摘要与 latest 明细
    4. 给前端提供一个AccountStatus字段用于判断用户状态

        1. 单次取消预约

# 申请，系统消息，课程通知， 需要单独一个表
1. 用户互动表 user_interaction_notifications
    1. MOMENT_LIKE， 用户给你的动态点赞
    2. COMMENT_LIKE， 评论点赞
    3. COMMENT_ADD， 添加评论
    4. COMMENT_REPLY， 回复评论
    5. MOMENT_MENTION， 有人提及你

2. 系统通知表 user_system_notifications
    1. USER_FOLLOWED， 用户关注了你
    2. CERTIFICATION_REVIEW， 认证任何通过
    3. ADMIN_BROADCAST， 举报结果+系统处罚
    4. MOMENT_MEDIA_AUDIT_REJECTED， 发布的动态未过审
    5. COURSE_MEDIA_AUDIT_REJECTED， 发布的课程未过审
    6. AVATAR_AUDIT_REJECTED， 发布的头像未过审
    7. BACKGROUND_AUDIT_REJECTED， 发布的背景图未过审
    
3. 课程通知表 user_course_notifications
    0. BOOKING_CREATED， 新的预约
    1. BOOKING_CANCELLED， 取消预约
    2. PAYMENT_SUCCESS， 支付成功
    3. COURSE_SALES_INCOME， 课程售出
    4. LESSON_SCHEDULED， 课程即将开始
    4. LESSON_STARTED，对方已确认上课，课程已开始
    5. LESSON_FINISHED，课程已结束
    6. BOOKING_REQUEST_RECEIVED，预约请求
    7. BOOKING_ACCEPTED，接受预约
    8. BOOKING_REJECTED，拒绝预约
